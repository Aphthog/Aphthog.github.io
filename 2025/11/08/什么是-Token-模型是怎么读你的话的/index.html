什么是 Token：模型是怎么读你的话的

发表于 2025-11-08 更新于 2026-09-11 分类于 技术笔记
模型不看字只看 token，BPE 拆分直觉，中文为什么更费 token

第一次看大模型的计费页面，我盯着”0.002 美元 / 1K tokens”看了半天——token 是什么？模型按什么单位算钱？后来才知道，模型压根不看字，它看的是 token。

我们的直觉是模型在读文字，就像人读句子一样。但底层实现里，模型看到的是一串数字编号。从文字到数字编号的中间层就叫 tokenization（分词），而每个被切出来的单元就是一个 token。

BPE：常见词不分家，生僻词被拆开

大多数主流模型用的分词算法叫 BPE（Byte Pair Encoding）。这个词听起来复杂，直觉很好理解：

  • 模型先统计大量语料里的高频词，把它们收进词表
  • 遇到一个词，先看它是不是常用词——如果是，整体编码成一个 token
  • 如果不在词表里，就拆成子词（subword）片段，直到每个片段都能在词表里找到

举个例子，”unbelievable” 这个英文单词在 BPE 下可能被拆成 “un” + “believe” + “able” 三个 token。而 “the”、”is”、”and” 这类高频词，每个词就是一个 token。

中文的处理方式不太一样。中文不具备天然的”单词空格分隔”，模型通常把每个常用汉字或常用词组当作一个 token 的基础单位。因为在 BPE 的语料统计里，高频出现的字和词会被保留。

同样的信息量，中文大约要 15–18 个 token。原因很简单：中文的”信息密度”相对于一个 token 能携带的信息量来说，不如英文高。英文里一个常见的完整单词就能做一个 token，中文里一个汉字只是一个字符，模型需要多个 token 才能表达一个完整的概念——“大模型”三个字就得至少 3 个 token。

这不是 bug，是词汇分布导致的统计结果——英文单词本来就比中文字符长，BPE 的”初始 token 单位”天然向英文倾斜。

上下文窗口和计费都按 token 算

理解 token 有一个非常实际的用处：不管你是用 ChatGPT 还是调用 API，所有东西都是按 token 计价的。

  • 上下文窗口：模型能”记住”的上限单位是 token，不是字数。一个 8K 窗口的模型大约能处理 6000 个左右的中文字，或者 8000 个英文单词。
  • 输入 vs 输出：你发给模型的 prompt 和模型返回的回复，两边的 token 都计费。输出 token 通常比输入 token 贵 3–4 倍，因为生成比理解更消耗计算资源。
  • 估算技巧：英文大约 1 个单词 ≈ 1.3 token；中文大约 1 个字 ≈ 1.5–2 token。快速估算时可以按这个比例。
内容 实际字数 大致 token 数
英文一句（10 个单词） 10 词 ~13 tokens
中文一句（15 个字） 15 字 ~23-30 tokens
一篇 1000 字中文博客 1000 字 ~1500-2000 tokens
一篇 500 词英文邮件 500 词 ~650 tokens

为什么开发者在乎这个

如果你只是在网页端和 ChatGPT 聊天，token 的概念可能不太影响你。但如果你在写 LLM 应用：

  • prompt 太长会被截断：模型有最大 token 限制，超出就会被默默切掉。中文开发者要对 token 更敏感——同样一段语义内容，中文占用的 token 更多。
  • 成本估算：你的业务一天处理 1 万次对话，每次平均多少 token，乘以价格，就是你的 API 账单。
  • 流式输出优化：流式输出时每次返回一个 token（或几个），速度感知取决于 token 生成的速度，和字数没有直接关系。

回到开头那个问题：token 就是模型的基本信息单位。理解了它，才算真的理解了大模型为什么”贵”、为什么”记不住那么多内容”、以及为什么写中文 prompt 要比英文更节省。
