垃圾回收入门：从 GC Roots 说起

发表于 2025-12-20 更新于 2026-09-11 分类于 技术笔记
引用计数缺陷、可达性分析、GC Roots 类型，分代假设与四种收集器概览

有一次在群里看到有人问”两个对象互相引用，GC 会不会回收它们”，我第一反应是”互相引用应该不会回收吧”——但仔细一想，如果互相引用就不回收，循环引用岂不变成内存泄漏了？写这段的时候我才发现自己连 JVM 怎么判断对象存活都没搞清楚。这篇就从这个问题入手，把垃圾回收的几条核心概念记下来。

引用计数法的缺陷

最直观的思路是给每个对象记一个”被引用的次数”：被引用计数加一，引用失效减一，到零就回收。但这个思路有一个绕不过去的缺陷——循环引用。

循环引用在代码里很常见——双向链表、父子节点、观察者模式都有。引用计数法处理不了这个，所以主流的 JVM 没有用它来判断对象存活（Python 等语言的做法是用引用计数加额外手段处理循环引用，但 Java 走了另一条路）。

可达性分析

JVM 用的是可达性分析（Reachability Analysis）：从一组称为 GC Roots 的根对象出发，沿着引用链遍历，走不到的对象就是不可达的，可以被回收。

用上面的例子来说：如果 a 和 b 都没有被任何 GC Roots 引用到，那从 Roots 出发就遍历不到它们——即使它们互相引用，JVM 也知道这些对象是垃圾。

GC Roots 有哪些

Roots 类型 包含什么
虚拟机栈中引用的对象 每个栈帧里局部变量表引用的对象
本地方法栈中 JNI 引用的对象 native 方法引用的 Java 对象
方法区中类静态属性引用的对象 static 变量指向的对象
方法区中常量引用的对象 字符串常量池等引用的对象
活跃线程 正在执行的 Thread 对象本身

举个例子：方法里的局部变量引用的对象、静态变量引用的工具类实例、常量池里的字符串——这些只要还在用，就不会被回收。

分代回收的假设

HotSpot 的分代设计基于一个统计规律：大部分对象朝生夕死——分配出来不久就成了垃圾。所以把堆分成年轻代和老年代：年轻代 GC 频繁但只扫部分内存，老年代 GC 间隔长。这个假设在大多数应用里成立，但不是绝对的——缓存类应用里对象活得久，需要调整分代参数或换收集器。

四种收集器一句话定位

不同 JDK 版本默认的收集器不一样。我本地用 JDK 17，默认是 G1。下面用表格定位——每种只说一句话，不展开：

收集器 一句话定位
Serial 单线程、Stop-The-World，适合几百 MB 以内的小堆或客户端模式
Parallel 多线程并行回收，追求高吞吐，JDK 8 默认就是这个
CMS 低停顿并发标记，不整理内存（JDK 9 标记废弃，JDK 14 正式移除）
G1 分区（Region）式收集，可预测停顿时间，JDK 9 起是默认收集器

这个表格只给个印象。每种收集器的参数细节和适用场景展开写又是一篇，但对于日常排查，知道”当前环境用什么收集器、它大致怎么工作”就够了。

GC 是 JVM 比较大的话题，这篇只涉及”怎么判断该回收谁”——下一篇顺着类加载机制走，讲讲 JVM 怎么把 .class 文件变成可执行的代码。
