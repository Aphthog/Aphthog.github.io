类加载机制入门

发表于 2026-01-17 更新于 2026-09-11 分类于 技术笔记
类加载的七个阶段，准备与初始化的区别，双亲委派模型及其意义

之前有次线上遇到一个 NoSuchMethodError，排查了半天发现 classpath 里有两份同名同包的类，系统加载了其中一份，跟调用方期望的不匹配。当时我对类加载的理解就是”从磁盘读个 .class 文件进来”，不知道 JVM 还有”加载过一次就缓存”的机制，更不知道一个类从文件到可执行对象要经过七个阶段。这篇从头到尾过一遍。

生命周期七阶段

一个类从被加载到被卸载，大致走七个阶段：

加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载

前五个（加载到初始化）是最关键的。

加载（Loading）

通过类的全限定名找到二进制字节流（通常是 .class 文件），把字节流中的常量池、字段表、方法表等结构解析成 JVM 内部的方法区数据结构，然后在堆上生成一个 java.lang.Class 对象作为访问入口。

验证（Verification）

确保字节流符合 JVM 规范，不会危害虚拟机自身安全。比如检查魔数（.class 文件开头一定是 0xCAFEBABE）、检查常量池类型是否合法、检查方法的字节码有没有跳转到不该跳的指令等。这是安全防护的第一道关卡。

准备（Preparation）

为类的静态变量分配内存并赋零值。注意，这时候赋的是类型的默认值，不是你在代码里写的初始值。

这个区别常被问到。准备阶段只是把静态变量清成该类型的默认值——int 是 0、引用是 null。真正调用你写的赋值语句，是在初始化阶段。例外是 static final 的基本类型或 String 常量——编译期就确定了，所以会在准备阶段直接赋好值，不走初始化。

解析（Resolution）

把常量池中的符号引用（类名、方法名等人类可读的标识）替换成直接引用（内存地址或句柄）。HotSpot 使用延迟解析——只在字节码真正用到某个符号引用时才去解析，不是一次性全部解析完。

初始化（Initialization）

执行 <clinit> 方法——把静态变量的赋值操作和静态代码块合并起来执行。这时 count 才变成 10，name 才变成”hello”。JVM 会保证 <clinit> 执行期间加锁，同一时间只有一个线程能初始化这个类——这就是”类加载是线程安全的”的来源。

双亲委派模型

加载阶段最关键的问题是”谁来加载某个类”。JVM 有三种内建的类加载器：

  • Bootstrap ClassLoader：最顶层的加载器，负责加载 rt.jar（JDK 9 之后是 java.base 等模块），由 C++ 实现，在 Java 中不可见
  • Extension / Platform ClassLoader：负责加载扩展库（JDK 9 起改名为 Platform ClassLoader）
  • Application ClassLoader：负责加载 classpath 上的代码，我们的类默认由它加载

它们的协作模式叫双亲委派：当一个类加载器被要求加载一个类时，它先把请求委派给父加载器，父加载器再往上委派，直到 Bootstrap 加载器。只有父加载器都找不到这个类时，子加载器才会自己尝试加载。

这解决了什么问题？防止核心 Java 类被替换。 比如你写了一个自己的 java.lang.String。按双亲委派的逻辑，Application ClassLoader 会委派到 Bootstrap，Bootstrap 发现已经装过 rt.jar 里的 String 了，直接返回。你的 String 永远不会被加载——即使 classpath 里摆着，系统也不会用。

打破双亲委派： Tomcat 要为每个 Web 应用维护独立的类加载器，保证不同应用的同名类互不干扰，所以重写了 loadClass() 先自己加载，加载不到才委派给父加载器。其他如 JDBC 的 SPI 机制、OSGi 也以不同形式打破了这套规则。双亲委派保证了隔离和安全，打破它则换来了灵活——什么时候该破、什么时候该守，取决于你对类隔离的需求有多强。
