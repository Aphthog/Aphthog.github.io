联合索引与最左前缀原则

发表于 2026-03-14 更新于 2026-09-11 分类于 技术笔记
联合索引(a,b,c)的最左前缀规则，explain对比验证，索引列顺序怎么定

上个月同事跑过来问：”我给 (a, b, c) 三个字段建了联合索引，为什么 WHERE a = 1 AND c = 3 走了索引，WHERE b = 2 AND c = 3 却没走？”这个问题背后就是最左前缀原则。

联合索引（也叫复合索引）的 B+ 树在排序时不是把三个字段拼起来算一个 key，而是先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。这意味着索引的使用必须匹配这个顺序：只有从左到右的连续前缀才能利用到索引的排序信息。

换句话说，(a, b, c) 这个联合索引等价于建了三个索引：

  • (a) —— 单独按 a 查，能用
  • (a, b) —— 按 a 和 b 查，能用
  • (a, b, c) —— 按三个字段查，能用

但 (b) 单独查、(b, c) 一起查，或者 (a, c) 跳过了中间的 b——都用不上完整的索引树。

EXPLAIN 验证

建一张测试表，插一些数据，看 EXPLAIN 的输出：

（以下结果基于 MySQL 5.7，数据量约 1 万行）

查询条件 key type rows 说明
WHERE a = 1 idx_a_b_c ref 少量 用到了 a
WHERE a = 1 AND b = 2 idx_a_b_c ref 少量 用到了 a 和 b
WHERE a = 1 AND b = 2 AND c = 3 idx_a_b_c ref 极少 全部用上
WHERE a = 1 AND c = 3 idx_a_b_c ref 少量 a 走索引，c 当过滤条件（不是在索引中定位）
WHERE b = 2 NULL ALL 1 万 没有走索引，全表扫描
WHERE b = 2 AND c = 3 NULL ALL 1 万 同样全表扫描

关键在于第四行：WHERE a = 1 AND c = 3 的 type 是 ref，说明确实走了索引。但 Extra 里会出现 Using index condition——表示 a 用索引定位了行，c 的部分是在存储引擎层做索引下推（ICP，Index Condition Pushdown），不是通过 B+ 树的排序来精确定位的。效率比 a=1 AND b=2 低，但比全表扫描好太多。

而 WHERE b = 2 直接走了 ALL 全表扫描，因为索引的排序首列是 a，没有 a 的限制，MySQL 不知道从 B+ 树的哪个位置开始遍历。

这里还有个常见误解：以为 WHERE a > 1 AND b = 2 能同时用上 a 和 b。其实一旦 a 是范围查询，b 就只能在结果集里过滤了——因为索引树上 a 相同的行才按 b 排序，a 的范围查出多条，这些行的 b 不保证有序，走不了索引的二分查找。这种情况 key_len 字段能看出来——只看 a 的长度，不包含 b。

索引列顺序怎么定

知道规则之后，实际建索引时该把哪一列放前面？两个原则：

原则一：区分度高的放前面。 性别字段只有男女两种值，区分度极低，建联合索引时放在最左边几乎没有筛选效果。反而像用户 ID 或订单号这种几乎每条记录都不同的字段，放左边能快速把范围缩小到个位数。实际计算可以用 COUNT(DISTINCT a) / COUNT(*) 来估一下。

原则二：按查询模式排。 区分度不是唯一标准。如果系统里 90% 的查询都按 status 筛选，而 status 只有 3 种取值（区分度低），但把它放第一个可以让绝大多数查询走索引——有时候这就是更优的选择。最终的决策是区分度和实际查询频率的权衡。

有一种常见策略是把等值查询的列放前面，范围查询（>、<、BETWEEN）的列放后面。因为一旦遇到范围查询，后面的列就都用不上索引了。比如索引 (a, b)，WHERE a = 1 AND b > 10 能用上 a 和 b，但 WHERE a > 1 AND b = 10 只有 a 能走索引，b 的条件是在结果集里过滤。

总结

最左前缀原则的本质是 B+ 树对多字段排序的方式：从左到右逐层排序，所以查询也必须从左到右连续匹配。理解了这个，写 SQL 和建索引的时候就能自己判断”这个联合索引能不能用上”。下次遇到类似的问题，跑一遍 EXPLAIN 就能确认。
