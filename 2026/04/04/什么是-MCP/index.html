什么是 MCP

发表于 2026-04-04 更新于 2026-09-11 分类于 技术笔记
工具接入标准化的背景，三个角色分工，协议的真正边界

去年做一个项目，接了三个不同的模型——GPT、Claude、GLM——每个模型都要单独写一套工具调用代码，参数格式不同、返回格式不同、错误处理方式也不同。当时就想，能不能把”模型怎么调工具”这件事标准化，写一次适配到处用？后来看到了 MCP（Model Context Protocol）。

问题背景：每个工具都要为每个模型接一遍

没有 MCP 之前，开发一个大模型应用通常是这样：

每个工具只为了实现”查询数据库”这一件事，就要为不同模型写三套接口代码。而且工具数量一多——搜索、文件读取、计算器、API 调用——维护成本就直线上升。

这个问题的本质是：模型厂商之间没有统一工具调用协议。MCP 想填补的就是这个空白。

MCP 的三个角色

MCP 把系统分成三层：

  • Host：用户直接接触的应用程序。比如 Claude Desktop 就是一个 Host，它负责管理对话、管理多个 MCP Server 的连接。
  • Client：Host 内部的一个组件，负责跟 MCP Server 建立连接、协商能力、转发请求。你在代码里集成的 MCP SDK 就是这个角色。
  • Server：实际提供工具和资源的服务。比如一个 sql-server 提供 SQL 查询能力，一个 filesystem-server 提供文件读写能力。

任何一个 MCP Server 只需要实现一次协议，就能被任何支持 MCP 的 Host 使用。这就解决了”每个工具为每个模型单独适配”的问题。

MCP 标准化的不只是工具

除了工具调用（tool），MCP 还标准化了资源访问（resource）和提示模板（prompt template）：

能力 类比 说明
Tools 可调用的函数 模型自主决定调不调、怎么调
Resources 可读取的数据 类似 REST 的 GET，提供给模型上下文
Prompts 预置的模板 开发者写好的 prompt 模板，用户直接选

这意味着一个 MCP Server 不仅能提供”搜索”这种动态操作，还能提供”用户手册.pdf”这种静态资源，以及”写周报”这种预置 prompt。覆盖了模型应用中最常见的三种交互模式。

老实说：这层协议解决的是工程重复，不解决模型能力

MCP 是个好东西，但它的作用域有限。我在项目里用上之后有几个体会：

好处很真实：同一个搜索工具只需写一个 MCP Server，任何 MCP 兼容的 Host 都能直接用。之前维护三套 tool format 的痛苦彻底消失。生态也在迅速丰富——社区已经有现成的 MCP Server 做文档搜索、API 封装等工作。

但别指望它让模型变聪明：MCP 解决的是”连接方式标准化”的问题，不是”模型推理能力”的问题。一个 MCP Server 写得再好，模型本身理解不了你的业务、编造参数、陷入循环——这些问题 MCP 一个都解决不了。它只是一条通信管道，不负责管道里面的”水”有多清。

实际部署复杂度：每个 MCP Server 都是一个独立的进程或服务。一个应用如果接了 5 个 MCP Server，就要维护 5 个进程的生命周期——启停、健康检查、故障恢复。这在本地开发时还好，上了生产环境就是一个额外的运维负担。

总的来说，MCP 让”模型接入工具”这件事从手工适配走向了协议化，是一个工程上的进步。但要清醒地知道它的边界在哪里——它不会让模型变强，只会让你接得更快。
