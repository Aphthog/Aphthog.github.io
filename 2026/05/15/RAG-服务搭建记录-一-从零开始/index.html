RAG 服务搭建记录（一）：从零开始

发表于 2026-05-15 更新于 2026-09-01 分类于 技术笔记
技术选型、架构设计、FAISS vs 其他索引方案

去年年底开始做一个语义搜索的小项目，目标是搭建一个轻量的 RAG 服务，能够对文档做稠密+稀疏混合检索，再用 cross-encoder 精排。前后断断续续写了一段时间，中间踩了不少坑，记录一下整个过程。

为什么做

市面上有不少 RAG 方案，但大多偏向”大模型+知识库问答”的场景——接一个 LLM，搭一个向量数据库，再做问答链路。这类方案部署重、依赖多、成本高。我想要的更纯粹——只做检索，不涉及生成。

具体来说有这几个需求：

  • 纯检索：不需要 LLM 做问答，专注在”搜得准”上面
  • 混合检索：既要语义匹配（搜意思相近但用词不同的内容），也要关键词命中（搜包含特定术语的内容）
  • 本地运行：不依赖外部服务，一台带 GPU 的笔记本就能跑起来
  • 多租户：不同的数据集需要隔离存储和检索
  • HTTP API：方便其他应用和前端调用

所以这是一个非常聚焦的检索服务，不做对话、不做生成、不做知识库问答。纯搜索。

嵌入模型选型

嵌入模型负责把文本变成向量，是整个检索系统的基础。选型时对比了几个方案：

sentence-transformers/all-MiniLM-L6-v2

轻量（~80MB），速度快，英文效果好。但中文效果一般，而且输出维度只有 384，对细粒度语义的表示能力有限。pass。

BAAI/bge-large-zh-v1.5

专门面向中文的嵌入模型，1024 维输出，中文效果很好。但只支持稠密向量，没有稀疏能力。依赖 sentence-transformers 库加载，这个库在 Windows 上有稳定性问题（后面踩坑篇细说）。

BAAI/bge-m3（最终选择）

bge-m3 是一个多语言、多功能（Multi-task、Multi-lingual、Multi-dimension）的嵌入模型，它的特殊之处在于同一个模型能同时输出稠密向量和稀疏向量。

为什么这很重要？纯稠密检索依赖”语义压缩”，把整段文本压到一个固定长度的向量里，查询时找向量最近邻。这对于同义改写、语义相近的内容效果很好，但对于关键词精确匹配——比如搜”确定首句”就希望结果里一定有这个短语——纯稠密的方式可能会漏掉。稀疏向量正好补充了这个短板，它本质上是一个词汇权重向量，每个 token 的位置记录了该 token 对文本语义的贡献度，做检索时算的是词汇级别的交集。

bge-m3 同时输出 1024 维稠密向量和 65536 维稀疏向量，前向一次就够了，不需要维护两套独立的编码管线。

BAAI/bge-reranker-v2-m3

在初排之上加了一个精排层。bge-reranker-v2-m3 是一个 cross-encoder，把查询和文档拼成一对输入，输出一个相关性分数。双编码器把查询和文档独立编码，两者之间没有交互，cross-encoder 则让它们在注意力层直接交互，打分更准。代价是慢——每对文本都要过一次模型，所以只对粗召回的前几名做精排。

向量索引选型

选型时主要考虑的是在笔记本上本地运行，排除了需要部署独立服务的方案（Milvus、Qdrant、Elasticsearch 等）。

FAISS

Meta 开源的向量检索库，C++ 实现、Python 绑定，性能非常好。支持多种索引结构：暴力（Flat）、倒排（IVF）、量化（PQ）、图（HNSW）等。

这里选的是 IndexHNSWFlat。HNSW（Hierarchical Navigable Small World）是一种基于图的近似最近邻索引，建图时每个向量作为图中的一个节点，M 参数控制最大连接数（设 32），搜索时从顶层图开始逐层向下贪心遍历。它的特点是搜索速度随数据量增长呈对数增长，在百万级数据量下能做到毫秒级响应。

建图参数 efConstruction（设 200）控制建图时的搜索宽度，值越大图质量越高但建图越慢。搜索参数 efSearch（设 512）控制搜索时的宽度，值越大召回越准但搜索越慢。

FAISS 用 L2 距离做度量，如果向量做过 L2 归一化，L2 距离等价于余弦相似度（因为 ||a-b||² = 2 - 2cos(a,b)），所以代码里在入库和查询时都调用 faiss.normalize_L2() 做了归一化。

稀疏向量维度 65536，不适合用 FAISS，直接用 scipy.sparse.csr_matrix 存成 npz 文件，检索时暴力算内积。因为数据量不大（几百到万级别），暴力扫描的开销可以接受。

整体架构

最终的项目结构是这样的：

索引流程：

  1. 文档进入 → 语义切分器切成 300~1000 字符的块（chunk）
  2. 每个块经 bge-m3 编码，同时得到稠密向量和稀疏向量
  3. 稠密向量建 FAISS HNSW 索引、持久化到磁盘
  4. 稀疏向量存为 npz 文件
  5. 块的原始文本和 metadata 存入 JSONL

搜索流程：

  1. 查询文字经 bge-m3 编码
  2. 稠密通道：FAISS 召回 top-100
  3. 稀疏通道：暴力内积召回 top-100
  4. 两个通道的分数各自 min-max 归一化
  5. 加权融合（dense 0.7 + sparse 0.3）
  6. 取 top-50 候选，reranker 精排 top-5
  7. 返回最终 top-K

所有服务在单进程中运行，模型加载后常驻显存。好处是简单、部署成本低，缺点是横向扩展能力有限——不过对于个人项目和中规模数据集完全够用。
