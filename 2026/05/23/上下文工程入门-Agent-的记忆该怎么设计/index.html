上下文工程入门：Agent 的记忆该怎么设计

发表于 2026-05-23 更新于 2026-09-11 分类于 技术笔记
三层记忆划分，截断与总结的取舍，多轮对话上下文爆炸案例

做过一个多轮对话的 Agent，聊到第 20 轮的时候，prompt 已经超过 8000 token 了。每次请求光传历史消息就要花不少时间，而且模型开始”记不清”前面说了什么——不是记性差，是上下文窗口被冲淡了。

这个问题不是模型缺陷，是上下文工程没做好。模型给了一个有限窗口，你要决定往窗口里放什么、不放什么。

三层记忆架构

业界经过大量实践，基本形成了三层记忆划分：

短期记忆：最近几轮的完整历史

用户在当前会话里最近几轮的交流，应该完整保留。因为模型的回答需要精确引用用户刚说的内容。比如用户说”刚才说的那个地址再发一遍”——模型必须能看到之前的完整消息。

保留多少轮？取决于上下文窗口大小和你其他内容的需求量。一个常见做法是保留最近 5–10 轮完整的消息，再往前的内容进摘要。

长期记忆：检索出来的事实

如果对话跨越多天，或者涉及用户之前讨论过的复杂内容，全量保留历史不现实。这时候需要把历史内容向量化存起来，当前对话需要时再去检索。

这本质上就是 RAG——只不过检索的对象不是知识库，而是历史对话记录。比如两周前用户提到过”我家住在重庆市渝中区”，今天用户问”帮我推荐附近的火锅店”，Agent 需要从历史对话里检索出用户的地址信息。

摘要压缩：把早期内容浓缩

超出短期保留轮次的历史，不直接丢弃，而是用模型生成摘要。每次对话结束后，可以跑一个”总结本轮要点”的流程，把内容压缩成 2–3 句话，存入长期记忆。

摘要的代价是一次额外的模型调用，但如果设计得当，一次摘要能避免每次请求都携带大量历史 token，长远看是省钱的。

截断 vs 总结：怎么选

当上下文窗口不够的时候，有两个选择：

做法 优点 缺点
截断 零成本，直接删最早的 丢失信息，模型”失忆”
总结 保留要点 有调用成本，可能漏细节

这不是非此即彼，而是分层的：最近几轮用截断（保持精确），再往前用总结（压缩）。

一个多轮对话上下文爆炸的例子

假设一个客服 Agent 跟用户聊了 30 轮。没有记忆设计的情况下，prompt 大概长这样：

到第 30 轮时，prompt 里塞满了退换货的完整对话记录，占了 6000 多个 token。每次请求都要传这 6000 token，API 费用按 token 算——而且模型要在这 6000 个 token 里找到”地址”相关的信息，注意力被大量无关内容分散。

处理方式是：

  1. 保留最近 5 轮完整对话（约 1000 token）
  2. 前 25 轮生成摘要：”用户要求退换 ORD-2025-001，已确认原地址发货，等待物流揽收。”
  3. 用户问”我刚才说的地址是哪个来着”时，从摘要中无法定位 → 再额外检索第 12 轮附近的具体地址对话

这样一来，每次请求的 prompt 约 1500–2000 token——比原来的 6000+ 省了三分之二，模型回答质量也明显提高。

上下文窗口是 Agent 应用里最容易忽略的瓶颈。每次迭代都看一下你的 prompt 有多长，长出来的那些 token 是不是真的需要——这个习惯比任何高级架构都管用。
