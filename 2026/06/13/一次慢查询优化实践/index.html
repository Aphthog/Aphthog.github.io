一次慢查询优化实践

发表于 2026-06-13 更新于 2026-09-11 分类于 技术笔记
列表接口P99从200ms涨到2s排查过程：慢查询日志、深分页根因、延迟关联改写

周三下午，测试环境的接口监控报警：订单列表页的 P99 延迟从平时的 200ms 飙到了 2s 以上。我心里咯噔一下——业务量没涨，代码也没上线新版本，问题大概率在数据库。

先看慢查询日志。MySQL 可以配置 slow_query_log = 1 和 long_query_time = 1，超过 1 秒的 SQL 会被记录下来。翻日志，找到那条拖垮接口的 SQL：

LIMIT 100000, 20——翻到第 5000 页了。接口是支持翻页的，正常情况下用户不会翻这么多页，但有个定时任务会逐页遍历全量数据做统计，跑到后面就爆炸了。

EXPLAIN 确认

EXPLAIN 一看：

type key rows Extra
ALL NULL 130 万 Using where; Using filesort

问题很清楚：

  1. type = ALL：全表扫描。status 没有索引，ORDER BY create_time 也没有索引。
  2. Extra 有 filesort：需要对 130 万行做排序，再取最后 20 条。
  3. LIMIT 100000, 20：MySQL 不是直接跳到第 10 万条开始取的——它会先查出满足条件的全部行和排序，然后扔掉前 10 万条。翻的页越深，丢弃的数据越多，耗时就线性增长。

深分页的根因

数据库里的翻页和人类翻书不一样。LIMIT 100000, 20 真正做的事情是：先找 100020 条，再扔掉前面的 100000 条。扫描的行数 = offset + limit。offset 越大，读的越多，跟加不加索引关系不大——走索引也得读那么多条。

这就是”深分页”问题的本质：offset 越大，MySQL 扫描和丢弃的数据就越多，时间就越长。

优化：联合索引 + 延迟关联

第一步，加联合索引。查询条件是 status = 1 然后按 create_time 排序，所以建：

这个索引能让 WHERE status = 1 走索引（type = ref），ORDER BY create_time 直接在索引上完成排序，去掉 filesort。但深分页的问题还在——即使走索引，LIMIT 100000, 20 仍然需要扫描 100020 条索引记录。

第二步，改成延迟关联（Deferred Join）。核心思路是：只让索引覆盖查询去定位需要的主键 ID，再用这些主键 ID 去回表取整行数据。这样回表只需要 20 次，而不是 100020 次。

内层子查询只查 id 字段，(status, create_time) 联合索引已经覆盖了——不需要回表，直接在索引树上完成排序和分页，只扫描 100020 条索引记录，拿到 20 个 id。

外层再根据这 20 个 id 回聚簇索引取整行，只做 20 次回表。

优化前后对比

指标 优化前 优化后
type ALL（全表扫描） ref
rows 130 万 约 100020（索引扫描） + 20（回表）
Extra Using where; Using filesort Using index（子查询）
耗时（P99） ~2s ~50ms

优化后耗时从 2 秒降到了 50 毫秒。子查询里的 SELECT id 走覆盖索引，外层回表只有 20 行——数据量对这个查询不再是瓶颈。

补充思考

延迟关联不是万能的。如果 offset 巨大（比如翻到第 100 万条），索引扫描仍然要扫 100 万条记录，即使不回表也有开销。对于这种场景，更好的方案是基于游标的翻页：不用 LIMIT offset, limit，改成 WHERE create_time < 上次最后一条的 create_time ORDER BY create_time DESC LIMIT 20，这样每次都是 O(1) 的定位。缺点是翻页不连续（不能直接跳到第 N 页），和产品设计有关，不是所有场景都适用。

总结

这次排查让我对深分页有了很具体的认识。LIMIT 100000, 20 不是”跳到第 10 万条然后拿 20 条”，而是”先数 100020 条、扔掉前 10 万条”。联合索引解决了 filesort 问题，延迟关联把回表次数从 100020 降到 20。优化没有用高级技巧，就是把索引和数据访问的路径对齐——理解 InnoDB 怎么存数据和怎么扫描的，倒推回 SQL 改写就能找到方向。
