缓存穿透、击穿、雪崩：三个常被念错的名词

发表于 2026-07-11 更新于 2026-09-11 分类于 技术笔记
清晰区分缓存穿透击穿雪崩三个易混概念及对应解决方案

第一次面试被问到”缓存穿透是什么”，我脱口而出”就是缓存没扛住，全打到数据库了”。面试官追问”那击穿和雪崩呢”，我卡住了。后来才知道这三个词我全搞混了——它们虽然都跟缓存失效有关，但问题发生的范围和数据特征完全不同，解决方案也各有侧重。

穿透 —— 数据根本不存在

缓存穿透指的是请求的数据在缓存和数据库中都不存在。每次请求都穿透缓存，直接打到数据库。

一个典型的例子：用户查一个不存在的商品 ID，每次查询都先去缓存看——没有，再去数据库查——也没有，返回空。下一个请求又来，同样的流程。如果这种请求量一大，DB 就扛不住了。

有人会说”那不是给过期时间加个随机值就行”——这是错的。随机过期时间针对的是缓存存在但一起过期的情况，穿透针对的是数据本身就不存在。两码事。

对策：

  • 空值缓存：查数据库发现不存在时，也在缓存里写一个空值（SET key null EX 60），短时间内同类请求不会打到 DB。缺点是空 key 可能占内存，适合 key 空间可控的场景。
  • 布隆过滤器：请求来之前先用布隆过滤器判断 key 是否存在。需要把所有合法 key 预先加载到过滤器里（百亿级也可行），空间效率极高——几百万 key 只占几 MB。布隆过滤器说”不存在”就一定不存在，说”存在”可能有误判，但这对缓存场景问题不大。

击穿 —— 热点 key 突然过期

缓存击穿是一个热点 key 刚好过期，在高并发下大量请求同时打到数据库。

假设一个热搜词条，缓存失效时间到了，同时来了一万次请求。第一个请求发现缓存没有，去查 DB，还没写完缓存；其他 9999 个请求也发现缓存没有，全部去查 DB——数据库瞬间被冲垮。

对策：

  • 互斥锁：第一个请求发现缓存过期后，加锁去查 DB 并重建缓存；其他请求等待锁释放，从缓存拿数据。Redis 可以用 SET key value NX PX 做分布式互斥。缺点是会阻塞部分请求，增加响应时间。
  • 逻辑过期：缓存里存两个值——业务数据和过期时间戳。发现”逻辑过期”后，当前线程直接返回旧数据，只让一个线程去更新缓存（后台异步刷新）。适合能接受短暂数据旧值的读多写少场景。

雪崩 —— 大量 key 同时过期

缓存雪崩是大量 key 在同一时间过期，大量请求同时落库。宽泛点说，Redis 宕机导致全部缓存不可用也算雪崩。

规模上，雪崩是穿透的放大版——穿透是单个不存在 key，雪崩是大面积缓存失效。破坏力最大。

对策：

  • 过期时间加随机值：这是真正管用的场景。基础过期时间设为 3600 秒，再给每个 key 加一个 0–300 秒的随机偏移，避免成片同时过期。
  • 多级缓存：Redis 之上再加一层本地缓存（比如 Caffeine），即使 Redis 层大面积失效，本地缓存还能扛住一部分请求。
  • Redis 高可用：主从 + Sentinel 或者 Cluster，避免单点宕机导致全盘不可用。

对照表

概念 原因 范围 核心对策
穿透 数据不存在（缓存和 DB 都没有） 单个不存在的 key 空值缓存、布隆过滤器
击穿 热点 key 过期 + 超高并发 单个热点 key 互斥锁、逻辑过期
雪崩 大量 key 同时过期 / Redis 宕机 大面积 key 过期 + 随机、多级缓存、高可用

一个容易犯的错

“加随机过期时间”能解决什么？答案是雪崩，不是穿透，也不是击穿。

很多人面试时把三个混在一起答，面试官一句话”那随机过期时间解决了哪个”就露馅了。我的建议是记一段具体的场景，而不是背定义——想一下”不存在的数据”、”热点 key 刚过期”、”大面积一起过期”三个画面，对应起来就不会再记错。

总结

穿透查不存在，击穿打热点，雪崩一大片——三个词是”问题广度”的递进。面试考这个题通常不是考你记没记住定义，而是看你有没有在实际中踩过并发场景下的缓存坑。把对策说清楚，再补充一句”我们还在击穿场景里加了限流兜底”，会比你背出八种方案更让人觉得你干过这个活。
