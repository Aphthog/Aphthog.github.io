LLM 应用的成本与延迟：一次权衡记录

发表于 2026-07-18 更新于 2026-09-11 分类于 技术笔记
输入输出定价差异，三种延迟来源，四种节省策略，延迟比成本更影响体验

第一次把模型部署到线上时，我算了一笔账：一个用户的单次对话，光 API 费用就几毛钱——如果日活上千，一个月下来开销不小。而且相比费用，用户反馈最多的其实是”等太久”。这篇文章记录我对 LLM 应用中成本与延迟的实测和理解。

token 成本怎么算

API 定价区分输入和输出，输出比输入贵 3–4 倍。以 OpenAI 的 GPT-4o 为例（参考价）：

方向 价格（每百万 token） 说明
输入 $2.5 你发的 prompt，用户的问题
输出 $10 模型生成的回答

为什么输出更贵？因为生成 token 需要逐字推理，每一步都取决于上一步的结果，无法并行。而输入 token 可以一次并行处理。

单次不贵，但一天 1 万次对话就是 $80，一个月 $2400。中大型业务光模型 API 就能烧掉不少钱。

延迟的三个来源

成本之外，延迟是最影响体验的因素。LLM 应用的延迟主要来自三个地方：

  1. 首 token 时间（TTFT）：从你发出请求到模型返回第一个 token 的时间。通常几百毫秒到几秒不等。受模型大小（稀疏 MoE 比密集模型快）、请求排队、网络延迟影响。

  2. 生成速度：第一 token 之后，模型每秒钟生成多少 token。GPT-4o 大概 30–60 token/s。这意味着一个 300 token 的回答需要 5–10 秒才能完整输出。

  3. 串行调用次数：如果你的 Agent 需要连续调用 3 次 API（先理解意图、再查资料、再生成回答），总延迟 = 3 × (TTFT + 生成时间)。这是最容易忽略的延迟放大因素。

场景 TTFT 生成时间 串行次数 总延迟
单轮问答（100 token 回复） 0.5s 2s 1 ~2.5s
单轮问答（500 token 回复） 0.5s 10s 1 ~10.5s
Agent 3 轮工具调用（每轮 300 token） 0.5s × 3 6s × 3 3 ~19.5s

超过 10 秒用户就能明显感知”慢”，超过 20 秒大部分用户会流失。

常见的省法和加速策略

结果缓存

如果用户查相同的问题（比如”你们公司的退货政策是什么”），第一次请求之后把结果缓存起来。相同的输入直接返回缓存结果，零延迟、零成本。对于高频问问题很管用。

并行工具调用

Agent 需要调多个工具时，如果工具之间没有依赖关系，调并行而不是串行。比如查”北京的天气和空气质量”——应该同时调天气 API 和空气质量 API，而不是等天气查完再查空气。

流式输出

不要在模型生成完所有 token 后才一次性展示给用户。用流式输出，生成一个字展示一个字。用户感受到的”首 token 时间”大幅缩短——虽然总生成时间没变，但用户觉得”它已经在回答了”。

老实说：多数场景延迟比成本更影响体验

写了几个 LLM 应用之后，我的真实感受是：成本是可以规划的，延迟是不可妥协的。

成本高，你可以优化 prompt 长度、做缓存、选便宜模型，有明确的操作方向。但延迟是用户直接感知的——一个 3 秒回复和一个 15 秒回复，在用户眼里是天壤之别。Token 贵了可以多卖一点服务来覆盖，但体验慢了用户下次就不来了。

最后一句话总结这篇回顾：做 LLM 应用，先把延迟压到 5 秒以内，再考虑降成本。流程冗余比模型贵更值得优先解决。
