Redis 持久化：RDB 与 AOF

发表于 2026-07-25 更新于 2026-09-11 分类于 技术笔记
RDB快照与AOF命令追加两种持久化策略的对比与选择

有次项目上线前，测试环境的 Redis 意外重启了。重启完我一查，缓存里有些数据没了——心里咯噔一下，幸亏是测试环境。但这也让我认真想了一件事：如果线上 Redis 挂了，数据能恢复多少？这就取决于持久化怎么配的。

Redis 默认把数据放在内存里，重启后内存清空，数据就没了。持久化的作用就是把数据从内存写到磁盘，下次启动时再读回来。Redis 提供了两种方式：RDB 和 AOF，功能各有侧重。

RDB —— 定期拍快照

RDB 是 Redis 默认开着的持久化方式。它把某个时间点的全量数据生成一个二进制快照文件（默认 dump.rdb），紧凑且恢复速度快。

触发方式有两种：

  • 手动：SAVE（阻塞，前台直接写，等写完才响应其他命令）；BGSAVE（fork 子进程，子进程写 RDB 文件，主进程继续响应命令）。生产环境永远用 BGSAVE。
  • 自动：在配置里设触发条件，比如 save 900 1 —— 900 秒内至少 1 次写操作就自动 BGSAVE。通常配三条递减的条件覆盖不同写入频率。

RDB 恢复确实快——加载二进制文件，不需要重放命令。但缺点也很明显：两次快照之间的数据丢了就是丢了。每 5 分钟一次 BGSAVE，那宕机最多丢 5 分钟数据。

AOF —— 记操作日志

AOF（Append Only File）记录的是每一条写命令，类似 MySQL 的 binlog。恢复时重新执行一遍所有写命令，重建数据。

AOF 有三级刷盘策略，通过 appendfsync 配置：

配置项 行为 安全性 性能
always 每条写命令都同步写入磁盘 最多丢一条命令 最慢
everysec 每秒刷一次盘 最多丢 1 秒数据 适中
no 由操作系统决定何时刷盘 可能丢较多数据 最快

生产环境几乎都用 everysec——兼顾安全和性能，最多丢 1 秒数据。

AOF 重写：AOF 文件随着运行时间会越来越大。BGREWRITEAOF 命令重新生成一份 AOF，只保留恢复当前数据集所需的最少命令。比如对一个 key 做了 100 次 INCR，重写后合并成一次 SET key 100。Redis 2.4 以后也支持自动触发，配置 auto-aof-rewrite-percentage 100 和 auto-aof-rewrite-min-size 64mb。

混合持久化（Redis 4.0+）

从 Redis 4.0 开始支持混合持久化，配置项是 aof-use-rdb-preamble yes。

混合模式在做 AOF 重写时，把当前内存数据先生成 RDB 快照写到 AOF 文件头部，再追加重写期间的增量命令。恢复时先加载 RDB 部分（快），再重放少量增量命令。兼具 RDB 的恢复速度和 AOF 的数据安全。

生产环境怎么选

考量维度 RDB 优先 AOF 优先 混合模式
数据安全性要求低 可以接受丢几十分钟数据 — —
数据安全性要求高 — 最多丢 1 秒 推荐
恢复速度优先 RDB 最快 大文件恢复慢 接近 RDB
磁盘空间紧张 RDB 文件更小 AOF 文件较大 略大于 RDB

大多数生产场景可以用这种配置：

  • 对数据安全要求高（比如订单相关的缓存）：appendonly yes + appendfsync everysec + aof-use-rdb-preamble yes
  • 纯缓存层，重启时能从别的来源重建：只开 RDB 默认配置即可
  • 两者都开着也是可行的——Redis 重启时会优先用 AOF 恢复（如果 AOF 开着），因为 AOF 数据更完整

无论选哪种，有个经验是定期把 RDB 文件备份到异地存储。Redis 本身不提供多副本备份，持久化文件的冷备要靠你自己。

总结

RDB 是快照思维，恢复快但丢数据多；AOF 是日志思维，丢得少但恢复慢；混合模式取两者之长。选持久化策略本质上是个 RPO（恢复点目标）的权衡——你能接受丢多少数据，就对应配到什么程度。
