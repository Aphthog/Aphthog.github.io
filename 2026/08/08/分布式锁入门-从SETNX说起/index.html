分布式锁入门：从 SETNX 说起

发表于 2026-08-08 更新于 2026-09-11 分类于 技术笔记
从SETNX到Redlock的分布式锁实现与常见坑点

第一次用 Redis 做分布式锁，锁没释放把整个流程拖垮了。

那时项目从单机架构拆成了多实例部署，原来的 synchronized 不跨进程，得换个方式。我搜了一下，用 Redis 的 SETNX 命令——key 不存在才能设成功，这不就是锁定吗？做完觉得挺简单。上线当天就出事了：一个请求拿到了锁，执行业务时抛异常退出了，锁没释放。后续所有请求都卡在等锁上，服务大面积超时。

后来仔细研究才发现，分布式锁看着简单，但实现正确比想象中难得多。

单机锁为什么不行

单机架构下，同一个 JVM 内的线程共享内存，synchronized、ReentrantLock 都管用。但在负载均衡的多实例部署下，请求被分发到不同的机器上，A 机器获取的锁对 B 机器不可见。所以需要一个所有实例都能访问的中间件来做仲裁——Redis 就是一个选择。

主从切换下的锁失效

但即使这样写了，还有一个更隐蔽的问题。

Redis 通常配主从架构。如果客户端 A 在主节点上成功设了锁，主节点还没来得及把这条写入同步到从节点，主节点就挂了。哨兵选举了一个从节点升为主节点——但新的主节点上没有那条锁记录。这时候客户端 B 也能拿到同一把锁。两个客户端同时持有同一把锁，分布式锁的前提就破了。

这是个真实存在的问题。虽然大多数业务场景下这扇窗口很小（主从同步通常是毫秒级），但如果你的系统对互斥性要求极高（比如资金类操作），这个窗口是不能忽略的。

Redlock 及其争议

Redis 作者提了一个叫 Redlock 的算法来解决这个问题：在 N 个独立的 Redis 节点（奇数，通常 5 个）上依次申请锁，超过半数成功就算拿到锁。

但 Redlock 也有争议。分布式系统专家 Martin Kleppmann 指出两个问题：

  • 时钟漂移：如果某个节点的系统时间发生跳变，锁的过期时间判断就不准了。Redis 的过期时间依赖系统时钟。
  • GC 暂停：客户端拿到锁之后发生了一次长时间的 Full GC，锁实际已经过期，但客户端不知道，还在继续在临界区内操作。

这两点至今没有完全服众的解决方案。Redlock 在严格意义上不是一个安全的分布式锁——它牺牲了部分安全性来换取可用性。

诚实的小结

对于大多数业务系统（非金融级强互斥），上面说的 SET NX PX + Lua 释放就够用了。日志里监控好锁的获取和释放，超时时间根据业务耗时合理设定（通常是业务最大耗时的 3–5 倍），再打一条 WARN 日志记录锁等待超时的情况。

如果你的系统真的不能容忍任何并发冲突——比如涉及资金变动、库存扣减——那 Redis 分布式锁可能不是你最好的选择。可以考虑用 ZooKeeper 的临时顺序节点，或者 etcd 的租约机制，它们在 CAP 中更偏 CP（一致性），锁的安全性更高。Redis 做分布式锁的核心优势是性能好、实现简单，代价是极端情况下锁有失效的可能——提前知道这个取舍，比出事再后悔要好。
