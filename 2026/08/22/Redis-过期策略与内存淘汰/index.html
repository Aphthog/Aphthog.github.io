Redis 过期策略与内存淘汰

发表于 2026-08-22 更新于 2026-09-11 分类于 技术笔记
Redis惰性删除与定期删除的配合及八种淘汰策略的取舍

项目上线两个月，Redis 内存满了，新的写入全部报错。我一脸懵地去看——给每个 key 都设了过期时间，为什么内存还是爆了？

后来才明白，给 key 设过期时间不代表到时它就会被”删掉”。Redis 的删除机制有两层：过期策略管”到期的 key 怎么删”；淘汰策略管”内存不够了怎么腾空间”。两者是两回事，混在一起想容易出问题。

过期策略：惰性删除 + 定期删除

惰性删除：每次访问 key 的时候，检查它是否已过期，过期就删掉再返回空。这是被动策略——如果一个 key 过期后没再被访问，它就赖在内存里不走。

定期删除：Redis 每隔 100 毫秒左右，从设置了过期时间的 key 集合里随机抽一批检查，过期就删。不是扫描全部 key——全扫的话几百万 key 要卡很久。每次只抽一小部分（默认 20 个），如果过期比例超过 25%，就再抽一轮。

两者配合下来，大部分过期 key 能在合理时间内被清理。但明显有一个漏洞：大量 key 同时过期后不再被访问，惰性删除碰不到它们，定期删除又只抽一小部分。这些 key 就会一直在内存里占着位置。这就是我当初踩的坑——key 过期了不代表内存会立刻腾出来。

内存淘汰：八种策略

当 maxmemory 达到上限后，Redis 不会坐以待毙，而是按配置的淘汰策略决定踢哪些 key 出去。Redis 提供了八种策略，从简单到精细：

策略 淘汰范围 淘汰方式
noeviction 不淘汰 写入直接报错
allkeys-lru 所有 key 淘汰最近最少使用的
allkeys-lfu 所有 key 淘汰最不经常使用的
allkeys-random 所有 key 随机淘汰
volatile-lru 设置了过期时间的 key 淘汰最近最少使用的
volatile-lfu 设置了过期时间的 key 淘汰最不经常使用的
volatile-random 设置了过期时间的 key 随机淘汰
volatile-ttl 设置了过期时间的 key 淘汰剩余 TTL 最短的

最常用的两个是 allkeys-lru 和 volatile-lru，它们的差别一句话讲清楚：如果所有 key 都设了过期时间，两个表现一样；如果有的 key 没设过期时间（比如存配置或永不过期的数据），volatile-lru 永远不会淘汰这些无过期 key，而 allkeys-lru 会一视同仁。

一般场景推荐 allkeys-lru，你在 Redis 里存的数据大概率都是”丢了不可惜”的缓存，不需要照顾谁。如果有类似”业务配置永不过期”的 key 想保护，才用 volatile-lru。

LRU 和 LFU 的差别：LRU 看最近一次访问时间，一个 key 刚被访问过就进入”热”区；LFU 看访问频率，一个 key 过去一小时被高频访问但最近几秒没碰，LFU 仍认为它重要。对周期性波动的业务（比如饭点的外卖热点），LFU 可能更准。

maxmemory 该怎么配

默认 64 位系统 maxmemory 为 0（不限制）。如果只是实验环境没问题，但在生产环境一定要配。配多大？

建议是：留出 20–30% 的内存给 Redis 自身和操作系统。比如服务器有 8GB 内存，Redis 的 maxmemory 设 4–6GB。不设那么满的原因有好几个：

  • 主从复制需要 replication backlog（默认 1MB，大流量时可能要更大）
  • AOF 重写和 BGSAVE 需要 fork 子进程，fork 期间 copy-on-write 会额外耗内存
  • 操作系统本身也需要内存做文件缓存

一般来说 maxmemory-policy 配 allkeys-lru，maxmemory 留余量，这个组合覆盖了 80% 的业务场景。

排查思路：”内存莫名满了”怎么办

遇到 Redis 内存涨得异常快，可以按这几步摸一下：

  1. redis-cli --bigkeys：扫描全库，按类型统计最大的 key。常见情况是某个 Hash 或 ZSet 被塞了太多数据没控制，或者 List 做了消息队列没有及时消费。但注意这个命令对线上有性能开销，建议在低峰期跑。

  2. MEMORY USAGE <key>：查看某个 key 实际占了多少字节。有时候你以为存的只是一个小字符串，但 SDS 加上过期时间等元数据开销可能比你预想的大。

  3. 检查过期时间：redis-cli -c -h <host> --scan --pattern '*' | xargs -I {} redis-cli TTL {} 统计全库 key 的 TTL，如果大量 key 的 TTL 设为 -1（永不过期），说明代码里有些 key 忘记设过期时间了。

  4. 查业务日志：某个 key 来源的业务是否在最坏情况下产生数据量远超预期——缓存了一条”用户的所有操作记录”结果用户操作了上万次。

总结

过期策略管的是”时间到了怎么删”，淘汰策略管的是”空间不够了踢谁”。后者是保命用的。配好 maxmemory 和 maxmemory-policy，再配合 --bigkeys 定期巡检，Redis 的内存问题大部分能提前发现。别等到 OOM 了再去看——到那时 Redis 可能已经开始拒绝写入了。
