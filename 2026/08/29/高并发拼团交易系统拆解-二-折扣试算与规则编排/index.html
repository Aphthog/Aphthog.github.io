高并发拼团交易系统拆解（二）：折扣试算与规则编排

发表于 2026-08-29 更新于 2026-09-01 分类于 技术笔记
系列第 2 篇：试算接口的规则树编排、DCC 动态开关、策略模式的 Map 注入路由、模板方法收敛公共逻辑，以及 500ms 到 200ms 的并行化推导

试算接口——用户打开拼团页看到”XX 元拼团结算”——是全系统流量最大的入口。这一篇拆它的两件事：编排（一堆校验和计算按什么顺序跑、怎么优雅降级）和计算（四种折扣怎么算、怎么扩展）。

@DCCValue 是自研的一个注解（wrench 框架）：启动时把 downgradeSwitch 这个 key 以默认值 0 写进 Redis，并订阅这个 key 的变更；运营在管理端把值改成 1，Redis pub/sub 推到所有实例，字段值直接更新——不重启、不发版，秒级把试算接口整体降级。cutRange 同理：改成 30 就是只放 30% 的用户进来（按 userId 哈希），新功能灰度的标准打法。

大促场景里这类开关是保命符：下游 DB 有压力，第一反应不该是扩容，而是把非核心流量降掉。

数字怎么来的：面试时这么讲

串行耗时 ≈ T活动查询 + T商品查询 + T计算；并行后 ≈ max(T活动查询, T商品查询) + T计算。

假设单次 DB 查询 80150ms（含网络往返 + MyBatis 映射），再叠加参数校验、序列化和树路由的固定开销：串行全链路 ≈ 400600ms，并行后 ≈ 180~250ms。500ms → 200ms 就是这么来的——本地压测的观测值，绝对值随环境浮动，但量级可复现。面试时先讲结构（两路独立查询并行化、get(timeout) 统一收口），再给数字，并主动说明是本地压测口径——比报一个说不清来源的数字可信得多。

代码里还留了一个 MarketNode2CompletableFuture 的备选实现，源码注释里有张对比表，摘录要点：

对比维度 FutureTask CompletableFuture
任务编排 弱（手动管理多个 Future） 强（thenApply、allOf）
代码简洁性 冗余（显式 get()） 简洁（链式调用）
异常处理 繁琐（逐个捕获） 优雅（exceptionally 统一处理）
适用场景 简单任务 复杂异步编排

两路并行这种简单场景，FutureTask 够用；如果以后要”查询 A 的结果作为查询 B 的入参”这种带依赖的编排，就该换 CompletableFuture。切换实现只需换 @Service 注解——树框架把节点隔离得足够好，换内核不动外壳。

面试追问预演

Q: 为什么用规则树不是责任链？
A: 责任链是线性的”过五关斩六将”，任何一关拦下就结束；试算的流程有分支和旁路（无配置走 ErrorNode、数据缺失跳计算），树结构的 get() 显式表达”下一步去哪”，语义更贴。锁单那种纯串联校验，系列第三篇会看到用的就是责任链。

Q: 降级开关放 Redis，Redis 挂了怎么办？
A: @DCCValue 注解字段在 JVM 内存里有默认值兜底（downgradeSwitch:0），Redis 不可达时读的是本地缓存值，不会因为配置中心故障导致接口不可用。

Q: 线程池参数怎么配的？打满了怎么办？
A: 核心数按 CPU 密集为主配小值，队列有界，拒绝策略抛异常快速失败——试算是入口接口，宁可拒绝也不能堆积拖垮整台机器。get(timeout) 里的 timeout 是最后一道闸，两路查询超过阈值直接走降级分支。

Q: 金额为什么不能用 double？
A: 二进制浮点表示不了 0.1 这类十进制小数，累加会漂移；营销侧金额计算错一分都是资损事故。BigDecimal + compareTo + 向下取整是组合拳。
