高并发拼团交易系统拆解（四）：结算回调与退款逆向

发表于 2026-08-29 更新于 2026-09-01 分类于 技术笔记
系列第 4 篇：结算的三连条件更新、事务性发件箱保证回调必达、定时补偿与 Redisson 抢占、退款状态机的枚举路由、「团失败」到底由谁判定的状态机不闭环，以及整个系列的设计观总结

用户付完钱之后，故事才到一半：商城回调过来要结算成团，成团了要通知商城，用户要退款要逆向走一遍所有状态。正向流程决定了系统能不能用，逆向流程决定了系统敢不敢用。这一篇收尾。

事务性发件箱：回调必达的笨办法和好办法

朴素做法是在结算事务里直接发 HTTP。两个死法：

  • 事务里掺网络 IO 是反模式——HTTP 慢 3 秒，DB 连接被占 3 秒，高峰期连接池直接打穿；
  • 时序无解——先发消息后提交，事务回滚对方收到”幽灵通知”；先提交后发消息，应用崩溃通知就丢了。

发件箱的方案是把”要发消息”这件事本身变成业务数据：消息写入和业务变更同事务，要么一起成功要么一起失败。剩下的就是怎么把表里的任务投递出去——“即时 + 补偿”双通道：

  • 即时通道：结算事务一提交就扔线程池先试一把投递，绝大多数通知在一秒内送达，notify_status 直接置 1；
  • 补偿通道：定时任务扫 notify_status in (0, 2) 的记录重新投递，重试有上限——notifyCount > 4 标记彻底失败，防止下游挂掉时死循环打爆对方。

投递动作本身有并发防护，多实例部署时两把锁：

以及定时任务入口的 Redisson 抢占（tryLock(3, 60, SECONDS)）——谁抢到谁执行，防的是 N 台机器把同一份通知发 N 遍。整套设计与 Transactional Outbox 模式完全同构：没有 Canal、没有 Kafka 事务消息，一张表 + 一个定时任务换来至少一次投递保证。投递的是 at-least-once，所以下游（商城）还需要按 uuid 幂等去重——teamId_category_outTradeNo 这个幂等键就是为对方准备的。

这里的 end_time 值得单独解释——它不是活动结束时间，而是每笔订单自己的支付窗口：锁单落库前用 calendar.add(Calendar.MINUTE, activity.validTime) 算出”锁单时刻 + validTime 分钟”写进明细表。也就是说”到点”的计时从每个人锁单那一刻起算，15 分钟没付款就逐单逆向：明细退单、主表 lock_count - 1（where status = 0）、发 MQ 恢复 Redis 库存。

两个细节：limit 10 是批量的节奏控制，一轮最多处理 10 条，处理不完下一轮继续，避免大结果集拖垮任务；入口的 Redisson tryLock(3, 60, SECONDS) 保证多实例只有一个在跑。

还有一层要划清：这条超时链路是订单粒度的，它清理的是”没付钱的占坑者”，不会判定任何团队失败——团队状态机的真相下一节单独讲。

退款状态机：把路由写进枚举

退款是逆向流程的难点：拼团单有四种状态（拼单中/完成/失败/完成含退单），交易单有三种（锁定/完成/退单），两两组合九种，合法退款路径只有三种。把组合判断写成 if/else 会随状态增加而爆炸，这里的做法是状态机直接写进枚举：

每个枚举值自带 matches() 匹配自己的状态组合，非法组合在路由处就抛异常，不会漏到执行层。三种退款策略的差异用库存动作表达得最清楚：

  • 未支付退单（UNPAID_UNLOCK）：锁单量 -1，队伍名额重新打开，还能继续加人；
  • 已支付未成团（PAID_UNFORMED）：锁单量、完成量都 -1，人数缺口重新打开；
  • 已成团退款（PAID_FORMED）：最微妙——锁单量不恢复。队伍已经结算给了上游商城，动组队计数会影响已达成的交易；只把单状态改成”完成含退单”。如果队伍只剩这一个人，拼团直接转失败。

所有状态流转依然走条件更新。已成团退款在队伍主表上按 complete_count 分流成两条 SQL——除退款者外还有其他完成成员就转”完成含退单”，这是最后一个完成成员就直接转”失败”：

订单明细表的退单（group_buy_order_list.status -> 2）是另一条按 user_id + order_id 的条件更新，和队伍状态在同一事务里先后执行。并发退款、重复退单在 DB 层被最后拦截——和正向流程的原则一以贯之。

退单成功后，Redis 侧的库存恢复通过 MQ 异步完成，消费端三段式：本地消息表保证消息一定发出、SET NX("refund_lock_" + orderId) 保证不重复消费、MQ 重试保证失败必达——第三篇里那个时间单位 bug 就藏在这段代码里。

「团失败」到底由谁判定：状态机的一个不闭环

面试官问过我这个问题的变体：”拼团到点没凑满人，团失败由谁、在什么时机、怎么判定出来？”准备这题时我把全部 mapper 的 update 语句翻了一遍，结论有点反直觉——“到点没凑满”这个场景，代码里没有任何一行把团队置为失败。

把 status = 2 的写入点全部列出来，只有一个：paidTeam2RefundFail，条件是 (status = 1 or status = 3) and complete_count = 1。也就是上面说的已成团之后、最后一个完成支付的成员退款才触发——那是”人退光了团死”，不是”没凑满团死”。而超时链路里队伍主表只被 lock_count - 1，状态从头到尾停在”拼单中”。

所以”没凑满的团死了”在这个系统里是一个事实状态，不是状态位：lock_count 被逐单衰减归零、窗口全部过期，没有任何一行 update 宣判它失败。工程库的样例数据就是证据——好几支 target 3、lock 2、有效期早已过期的团，status 至今还是 0。更进一步的边界：超时扫描不碰已支付的单（out_trade_time is null 把它们排除在外），而锁单链路的三关校验（活动状态、参与次数、库存占用）查的是活动的窗口和额度，没有一处校验团队的 valid_end_time——于是一支”1 人已支付、还差 2 人、团队窗口已过、活动还在有效期”的团，理论上还能继续进人，永远不会被判负。未凑满的已支付成员想离场，只能自己走 PAID_UNFORMED 退款。

这是我主动写出来的设计现状：团队状态机不闭环——0 到 1（成团）有完整链路，0 到 2（超时失败）没有。危害在下游：上游商城能收到成团回调（notify_task 的发件箱链路），却永远收不到”团失败”回调，用户侧的待支付订单没有终态。合理的演进方向：超时扫描时顺带把”窗口已过且 lock_count 未涨”的拼单中主单批量终结为失败，复用 notify_task 发一条团失败 MQ；锁单链路加一关团队窗口校验；或者干脆把扫表换成延迟队列（Redisson DelayedQueue / 死信队列），锁单时按单投递、到点即处理，扫表变推送。

写在最后：三个设计观

四篇写完，这个项目给我的最大收获不是”会用 Redis 和 MQ”，而是三个设计观的校准：

  1. 正确性放 DB，性能放 Redis。INCR 和条件更新各司其职，别让缓存承担账本的职责；
  2. 幂等不是功能，是纪律。四处幂等四处打法，原则统一：唯一键 + 状态条件更新 + 抢占锁；
  3. 失败路径先于成功路径设计。恢复量 key、notify_task 重试上限、退款策略的”库存不恢复”、定时补偿——这些”失败了怎么办”的代码量一点不比正常流程少，而这正是交易系统和 CRUD 的分水岭。

面试追问预演

Q: 为什么不直接用 MQ 的事务消息/Canal 监听 binlog？
A: 都能解，但引一个中间件的运维成本和这套”一张表 + 定时任务”不成比例。发件箱的缺点是补偿有延迟（秒级），对成团通知这个场景完全够用。如果通知时效要求高到秒级必达、或者下游订阅方变多，再升级到 MQ 方案——表结构不变，投递通道可换。

Q: 重试上限为什么是 4 次？失败了人工介入？
A: 4 次是防止下游长时间不可用时无限重试的止损值，不是精心调优的结果。置为失败态后这条记录不丢，修复下游后可以人工重置状态重新投递；更完善的做法是失败告警 + 管理端一键重试。

Q: 已成团退款为什么不恢复锁单量？
A: 队伍已结算给上游，组队计数代表”这笔交易发生过”，是和商城对账的依据；恢复它会让商城侧的成团记录和营销侧对不上。退款的金额口径在订单上（status = 2），库存口径留在队伍上。

Q: 定时任务扫描会不会漏单/重复？
A: 扫描按状态条件（status=0、超时时间）圈定，处理完状态就变，天然不重复；单轮 limit 10 防止大事务，堆积分轮消化。多实例靠 Redisson 抢占，同一时刻只有一个实例在扫。

Q: 到点没凑满的团，最终状态是什么？谁来判它失败？
A: 这里我会主动指出设计现状：没人判。超时清理是订单粒度的（每分钟扫未支付单逐单逆向、lock_count 减一），团队主单状态永远停在拼单中——“团失败”是 lock_count 归零加窗口过期形成的事实状态，不是被置位的状态。全部 update 语句里 status=2 只有一个写入点：成团后最后一个完成支付成员退款（paidTeam2RefundFail，complete_count=1）。团队状态机 0 到 1 有、0 到 2 没有，上游收不到团失败回调，这是我指出现状后给出的演进点：扫描时批量终结过期主单 + 发件箱补一条团失败通知，或改延迟队列按单投递。
