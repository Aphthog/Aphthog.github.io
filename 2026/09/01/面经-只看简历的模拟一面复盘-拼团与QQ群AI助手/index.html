面经：一场只看简历的模拟一面（拼团 + QQ 群 AI 助手）

发表于 2026-09-01 分类于 技术笔记
只拿到简历的 AI 面试官 vs 以真实代码作答的候选人：11 道题完整复盘——条件更新两层保证、记账式库存恢复、SSRF 两个真洞当场认领，以及简历上那些经不起对账的数字

给自己安排了一场模拟技术一面：面试官是一个只拿到简历原文的 AI——它对两个项目的代码一无所知，所有问题都从简历表述里长出来；我以候选人身份作答，所有回答都锚在我逐行读过、本地调试过的真实代码上。一方代表”外人的视角”，一方代表”代码的事实”，两边对撞出来的东西，比单向背题有用得多。

这篇是全程复盘：11 道题的问答要点 + 每题的复盘笔记 + 面试官总评 + 我的修订清单。

拼团七连问

Q1 三个域怎么分的？域间怎么协作？

答：营销活动域、人群标签域、交易域，划分依据是生命周期——活动域的东西运营配置时就定死（读多写少），标签域是运营侧批量数据活（离线），交易域处理实时锁单支付退款（并发压力所在）。10 张表各归其主（活动 4、标签 3、交易 3）。域间协作有个刻意原则：跨域调用不发生在领域层之间——跨域编排在 trigger 层（Controller 注入两个域的领域服务，先试算后锁单）；交易域读活动配置走自己域的仓储接口，infrastructure 实现里做 PO 到窄实体的转换（防腐层变体）。同进程单体，实际是同步方法调用；数据同库共享是单体期取舍。

复盘：这题是准备最充分的一题，要点全部命中。两个加分动作：主动修正简历”7 张表”为 10 张；结尾主动交代”数据层同库共享”的诚实取舍——这句反而成了面试官下一题的钩子。

Q2 同库共享，工程上怎么防止腐化？

答：分两层，因为约束强度不一样。层与层是编译期强制——DDD 四层切成 Maven 模块，domain 的 pom 不依赖 infrastructure，领域代码想 import DAO 编译就过不去，这不是约定，是类路径上没有。域与域目前只是包级隔离——三个域是同一模块下的三个包，编译器拦不住跨包 import；实际防住靠收口（跨域访问只有仓储实现一个入口，review 面小）加评审纪律，没上 ArchUnit，这是短板。”能维持多久”：小团队能守，团队一大约定一定被冲破。下一步两件事：三个域拆独立 Maven 模块让依赖图像层间一样强制，ArchUnit 进 CI 兜底。

复盘：这题的题眼是分清”约定”和”机制”——很多候选人会把约定说成机制。主动承认域间没有强制手段，比含糊其辞可信得多；被追问”能维持多久”时给出成本排序的演进方案，是把短板答成规划感的关键。

Q3 完整试算链路 + 为什么责任链和规则树都要

答：请求进 Controller 先试算，试算内部是规则树：根节点进 Switch 节点读 DCC 动态配置（降级开关、切量比例，运营不发版可拨），过闸进 Market 节点——活动/折扣/人群可见性三路数据 FutureTask 并行加载，按计费类型从 Map 注入的策略集合选算法（直减/满减/折扣/N 元购四种，满减带分摊），最后 Tag 节点 Bitmap 判人群。树走完 Controller 转实体调锁单服务，锁单域内是责任链：活动可用性→参与上限→库存占用，顺序执行、不过即短路。五种模式各归其位：工厂在两条流水线的组装处，模板方法在节点骨架。树管”算”，链管”审”——树是带分支的决策编排（降级/切量/人群是条件分叉，新分支挂子树不动主干），链是无分支的短路流水线（顺序敏感、每关独立可单测）。去掉树，分支全成嵌套 if-else，加分支要改主干；去掉链，校验顺序隐式化、没法按关单测。

复盘：面试官明确说”不想听名词罗列”，所以每个模式都落到了具体调用点。结构辨析的落点句——树管算、链管审、分布在不同域不同阶段——是这题的灵魂，没有这句，前面链路背得再熟也只是复述。

Q4 线程池三连：参数、失败、隔离

答：先坦白前提：参数是工程模板默认配置，不是压测调优结果。yml 配置 core 20 / max 50 / 队列 5000 / CallerRunsPolicy——三路全是 DB/Redis 查询，IO 密集型，核心数高于 CPU 核数方向合理；CallerRuns 对在线接口等于天然背压（不丢请求、把压力传回调用方）。要挑毛病：队列 5000 偏大，大队列让 max 50 几乎永远触发不了（队列先填满），高峰期延迟恶化但表面看不出异常。一路失败的处理：现状 fail-fast，FutureTask 异常从 get() 以 ExecutionException 抛出整次试算失败；系统里真实的降级是粗粒度的（Switch 节点 DCC 开关整树降级）。改进按业务语义分层：活动/折扣路失败必须失败（无价可算），标签路可失败放行（Bitmap 不存在本就等于不限人群），get() 该加超时。隔离问题不用假设，现状就是共用——同一个全局池 bean 被试算、结算、退款补偿多处注入，后台任务灌满队列会把试算延迟一起拖垮，应该按”延迟敏感/吞吐型”分池加命名。

复盘：三连问的每一问都是”现状是什么 + 为什么这个方向 + 生产该怎么调”的三段式。承认参数不是压测出来的是全场最重要的诚实动作之一——校招没有生产调优经验是常态，装有的话一追就穿。

Q5 DB 回滚了，Redis 多占的名额怎么还？

答：同步记账，不是删也不是减。锁单服务在数据库事务失败时 catch 住，调 recoveryTeamStock——方法体就一行：对”恢复量 key” INCR，然后 rethrow 让事务回滚。为什么记账不减号：INCR 的返回值是排队序号，每个序号配了一把 SET NX 占位锁，decr 会让序号复用、并发下两个请求拿同一个号，把原子的东西搞乱；记账保持计数器单调，恢复量 +1 让占用判定条件”占用值 > 目标 + 恢复量”多放行一个人，语义等效归还。不还的后果：占用虚高、判定偏严、真实名额泄漏——但这是可用性问题不是超卖问题（方向是误拒不是误放，DB 条件更新兜底在更里面），且库存 key TTL 绑团队有效期，泄漏存续期有天然上限。退款侧同款机制加固版：MQ at-least-once 会重复消费，所以多一层 SET NX 以 orderId 防重——这里有个真 bug：锁的过期时间想设 30 天，毫秒值传成了分钟单位，实际约五万天，等于永不过期；方向保守（多锁不漏锁）不致命，但属于该修的技术债。

复盘：面试官后来说这道题”说明你不只是背方案”。这题能答好全靠把 occupyTeamStock 全文读过——“记账 vs 减号”的选择理由、”少卖不是超卖”的定性、30 天变 5 万天的 bug，都只在代码里。主动交代自己复盘出的 bug 比装干净加分得多。

Q6 发件箱的两个衔接点

答：写入时机：同一个本地事务——结算事务里依次做明细更新、进度加一、满员转完成、notify_task 插入，要么一起提交要么一起回滚。为什么必须绑：不绑只有两种时序——先插记录后提交业务，业务回滚了记录还在，下游收到幽灵通知；先提交后插记录，应用崩溃通知永久丢失。绑在一起，”业务发生”和”消息待发”在数据库层面原子成立，投递变成独立的 at-least-once 问题。状态机与重复：初始 0 → 成功置 1 → 未到上限失败置 2 → 超上限置 3 彻底失败；补偿任务每分钟扫 0 和 2。消息已送达但状态更新失败的场景明确会发生，所以上下游有契约：notify_task 的 uuid（teamId + 类别 + 外部单号）就是给下游幂等去重用的，上游不做 exactly-once 承诺，去重责任放在有天然业务键的下游。并发投递两把锁：任务入口 Redisson 抢占 + 单条投递 tryLock 等待 0 秒。重试上限有（notifyCount > 4 停），退避没有——固定每分钟一轮线性打 5 次，下游长故障时 5 分钟内全打完，该演进指数退避加告警。

复盘：”上游 at-least-once + 下游业务键去重”的分工表述是标准正解；退避缺失自己认了，面试官没有纠缠。这题的通用价值：任何”可靠性保证”都要能说出语义边界（保证什么、不保证什么、谁兜底），说不出边界的保证都是背的。

Q7 结算和退款并发打进来，状态怎么不乱？

答：没有应用层分布式锁——防并发的是”MySQL 行锁串行化 + 带状态断言的条件更新”。条件更新长这样：结算侧明细 where status=0、complete_count+1 where complete_count < target、主单 set status=1 where status=0；退款侧团队表 lock/complete 各减一 where status=0。每个 WHERE 都是对前置状态的断言，断言不成立影响行数 0，抛异常回滚。两个事务都更新同一条团队记录，InnoDB 行锁天然串行化。推两个时序：结算先提交——退款事务拿到行锁时读到”已成团”，退款路由按”团队状态×订单状态”组合选策略，自动变成成团后退款（锁单量不恢复，团队转完成含退单），账目语义正确；退款先提交——进度各减一，结算后到，complete_count 条件加一后没到 target，就不转主单不插通知，这次结算只是一次正常进度推进，不存在”发现人数不够就报错”的分支——满员判定不是结算的前置假设，是条件更新之后对既成事实的读取。兜底是两层的：路由层按读取状态选策略，执行层按提交状态拦截过期判断（读到旧值时 WHERE 不命中 → UPDATE_ZERO → 回滚 → 重试重新路由）。还有一点：这套正确性不依赖隔离级别玄学——UPDATE 是当前读，行锁加条件断言在读已提交下也成立。重复回调的幂等被同一套 WHERE 顺手解决。

复盘：面试官给的评价是全场最高——“真理解过并发控制才说得出来”。这题的方法论价值：并发场景题不要背结论，拿着具体的 WHERE 条件推时序，推得动就是真懂。

QQ-BOT 三问

Q8 “ReAct 循环”和”单次 LLM 调用”矛盾吗？

答：先纠正简历措辞——“单次调用”想表达单一入口、统一循环，不是字面只调一次，这词写得不对。实际机制：消息进统一工具循环，上限 5 轮，每轮调一次 chat_with_tools；模型返回 tool_calls 就并行执行、回填观察、续跑，返回纯文本就终止；实际调用 1 到 5 次，次数由模型自己决定。终止条件：文本回答，或 5 轮打满给兜底话术；斜杠命令和纯标点根本不进 LLM。概念掰正：这个循环本身就是 ReAct 的工程化（推理在模型内部完成，我负责行动执行和观察回填），砍掉的是五阶段流水线——Router/Planner/Executor/Reflector/Builder。这套真实现过、有单测，上线前整体拿掉，三个业务理由：延迟（群聊等 10 秒就挨骂）、故障面（五阶段可用性连乘）、收益错配（90% 请求是闲聊和单步查询，为极少数复杂任务让所有人陪跑）。

复盘：简历措辞被抓包，当场认 + 给准确版本，比辩解体面。“架构服务于场景，不是服务于架构图” 这句砍五阶段的总结，是整个 QQ-BOT 项目最值钱的一句面试话术。

Q9 SSRF：三个载荷能不能防住？

答：先定位：校验在工具入口做一次性判断（解析成 IP 再对七段私网列表），不在连接层。逐个过：http://0x7f000001/ 能防住但属侥幸正确——十六进制不是合法点分形式，走 DNS 分支，系统解析器按 inet_aton 语义转成 127.0.0.1 命中环回段；但把安全建立在 OS 解析器的宽容度上很脆弱，该显式拒绝非标准主机名。http://[::ffff:127.0.0.1]/ 防不住，真洞——IPv4 映射地址解析成 IPv6 后不命中任何黑名单网段，而 socket 连它会真落到环回；修法是校验前用 ipv4_mapped 展开映射段重查。302 跳 169.254.169.254 也防不住，同族真洞——校验只对原始 URL 做一次，客户端自动跟随重定向，每跳不重检；修法是关掉自动跟随、逐跳重跑校验、限跳数，终极方案是把校验点移到连接层（自定义 transport 在建连那一刻断言 IP），重定向和 DNS rebinding 的 TOCTOU 一起终结。

复盘：三个载荷一真防住、两真防不住，全认。面试官的评价是”比很多’防住了’的答案更有价值”。安全题答”防住了”之前先想想能不能被自己绕过——答不出绕过路径的”防住了”，在懂行的面试官眼里就是没做过。

Q10 语义记忆：写入、拼装、冲突

答：写入不是每条都存——回复发出后后台跑 LLM 抽取，取最近 6 条对话，”提取事实、没有输出 NONE”，NONE 哨兵让闲聊显式判空，temperature 0.1 + 200 token 封顶；窗口取 6 条防旧事实重复抽取。检索拼装：拿当前消息做 query，带 chat_key 过滤（群间隔离），top5 加前缀拼进上下文，模型看到的是”30 条顺序窗口 + 5 条语义召回”。咖啡冲突，实际机制：没有冲突消解，两条都进。语义记忆追加式存储两条共存；画像层是按键 upsert、同键覆盖（最后抽取的赢）。真实效果大概率偏向”他喝美式”——因为昨天那句在工作记忆窗口里且更近——但模型可能是蒙对的，不是系统保证的。演进三步：召回记忆带时间标注给模型做时序推理（成本极低、收益立现）；写入时相似冲突触发 LLM 裁决；用户主动纠错命令。

复盘：”模型蒙对不是系统保证”这句被面试官点名。把系统的实际行为和期望行为分开说，是所有 AI 工程面试的通用高分动作——模糊处不装精确。

收尾：JVM 场景题

Q11 试算 P99 从 200ms 涨到 2s，老年代持续攀升，怎么排查？

答：三步走。第一步找分水岭信号：jstat -gcutil 或 GC 日志，看每次 Old GC 结束后老年代能不能回到基线——回收后最低点阶梯式抬升是泄漏曲线；能清干净但很快灌满，是分配/晋升速率过高或堆太小。同时看时间相关性：发版、流量、新定时任务。第二步二分：jmap -histo 看 Top 对象不停机初筛；泄漏的特征是 Full GC 也挤不出空间。第三步定位引用链：jmap -dump 抓两份对比增量，MAT 看 Dominator Tree（找保留堆大的，不是对象本身大的）+ Leak Suspects + Path to GC Roots（排除弱软引用），看到哪个类哪个字段哪个集合攥着它；生产提前配 HeapDumpOnOutOfMemoryError，线上用 Arthas 不停机排查。结合本系统的三个嫌疑：ThreadLocal 没 remove（线程池复用线程，请求上下文随长寿线程泄漏）、无淘汰策略的静态缓存、线程池 5000 队列堆积（每个滞留任务攥着请求对象，内存和延迟一起恶化）。修复闭环：回归压测对比 GC 行为，把”GC 后基线”和”停顿 P99”做成告警项。

复盘：场景题的高分结构是路径 + 工具 + 数据 + 自家系统关联。”GC 后基线抬升当分水岭”是整题的锚；三个嫌疑点全部长在自己项目的真实结构上（试算线程池、DCC/Bitmap 缓存、大队列），这不是背的 JVM 八股能有的效果。

面试官总评

整体是近段时间面过的校招/实习候选人里完成度很高的一位，项目不是包装出来的，每个方案都能往下追三层而不塌方。最突出的亮点是工程判断力和诚实度——条件更新两层保证、库存”记账式恢复”、发件箱上下游语义分工这些都能讲到底层依据，而简历数字对不上、五阶段流水线砍掉、SSRF 两个真洞、重试无退避，全是自己先认的，这种”明知取舍且说得出为什么”的表态比无缺点的回答可信得多。短板集中在两点：一是严谨性——简历写 7 张表实际 10 张、”单次 LLM 调用”措辞误导、线程池参数和重试上限都是模板默认值，校招可以没有生产调优经验，但简历是你唯一能提前打磨的门面，数字和措辞必须经得起对账；二是几个自己识别出的待改进项（ArchUnit、指数退避、连接层校验、记忆时序标注）建议挑一两个真正落地，下次面试时”我做完了”的分量远大于”我知道该做”。建议评级：通过，可考虑往上一档定级。

复盘清单

简历要对账的数字（面试前必改）：

简历表述 代码事实
7 张数据库表 10 张（活动 4 + 标签 3 + 交易 3）
11 种注入正则 13 条（覆盖四类攻击向量）
“自动从 Python 类型注解生成 schema” 参数类型来自 params 字典显式声明，required 由 inspect.signature 推断
500ms → 200ms（提升 60%） 本地基准测试口径，需主动声明
“单次 LLM 调用” 单一循环、1~5 次调用、次数由模型决定

挑一个真落地（下次面试说”我做完了”）：指数退避 + 失败告警成本最低（notify_task 已有重试计数字段，退避就是扫描时的间隔计算）；ArchUnit 规则其次。连接层 SSRF 校验最重但最有区分度。

遗留强化点：线程池参数压测口径、JVM 排查的实操演练（本地造一个泄漏用 MAT 走一遍全流程）、Redis 主从/持久化对”Redis 不是账本”论点的支撑细节。

写在最后

这场面试最有价值的产出不是”通过”，而是三条元认知：

  1. 答案的长相取决于证据的深度。同一道”库存怎么回滚”的问题，背方案的人说”补偿机制”，读过代码的人能画出那行 INCR 并指出它的 5 万天 bug——差距全部来自有没有真的逐行读过自己的项目。
  2. 诚实是校招面试的杠杆而非风险。11 题里主动认的每一处（数字对不上、防不住、没退避、蒙对的）都没有变成减分项，反而全部成了”明知取舍”的证据。前提是认的时候要带上修法和边界。
  3. “我知道该做”和”我做完了”隔着一条简历的鸿沟。面试官最后那句提醒值得贴在墙上：识别出十个改进项不如落地一个。
