第一次写 Agent 循环的时候，我没有设最大轮数，结果模型在一个号码查询 API 上反复调了 30 次——每次都返回空，它每次都再查一遍。这是我学到的最重要的一课：Agent 必须有终止条件。

## 从一问一答到多轮自主

普通的 LLM 调用是"你问一句，模型答一句"的单次交互。Agent 的差别在于：**模型可能自己决定下一步做什么**——你再查一下数据库？再调一个 API？确认用户的意思？每一步它自己判断。

这就是"从被动回答变为主动行动"的转变。在项目里我第一次感受到这个区别是给 QQ 群做一个 AI 助手：普通调用只能回复消息，Agent 模式可以自己去爬网页、查资料、确认后再回答。

## ReAct 的思路：想、做、看

最流行的 Agent 循环模式叫 ReAct（Reason + Act）。思路其实很简单：

```
收到用户请求
    ↓
思考：用户需要什么？我有什么工具可用？（Think）
    ↓
行动：调一个函数、查资料或直接回答（Act）
    ↓
观察：刚才行动的结果是什么？（Observe）
    ↓
如果问题已解决 → 输出最终回答
如果还没解决 → 回到思考步骤
```

这就是"想一步、做一步、看结果"的循环。每次循环模型都基于最新信息做判断——可能继续行动，也可能确认任务完成。

实际代码里它大致长这样：

```
max_turns = 10
turn = 0
while turn < max_turns:
    response = llm.chat(messages, tools=all_tools)
    if response.has_tool_calls:
        执行工具调用 → 把结果加回 messages
    else:
        输出最终回答 → break
    turn += 1
```

## 循环的终止条件

上面那段代码有两个终止条件：

1. **模型没有要求调工具**，直接输出了最终答案。这是正常结束。
2. **超过最大轮数上限**，强行终止。这是安全兜底——防止模型陷入无限循环。

最大轮数设多少合适？看场景。一个查询天气的 Agent 可能 1–2 轮就结束了。一个需要调多个搜索 API 做调研的 Agent，可能需要 5–8 轮。我一般设 10 轮作为默认上限，然后根据业务调优。核心原则：轮数越少越好——每多一轮就多一次 API 调用，延迟和成本都翻倍。

## 什么时候该用 Agent，什么时候固定 workflow 就够了

很多人在接触 Agent 之后容易陷入"所有问题都想用 Agent 解决"的误区。现实是：**大多数场景更适合用固定 workflow，而不是 Agent**。

| | Agent | 固定 Workflow |
|---|---|---|
| 决策方式 | 模型自己判断下一步 | 代码写死流程 |
| 灵活性 | 高，能处理意外输入 | 低，只处理预设情况 |
| 可预测性 | 低，每次可能走不同路径 | 高，结果可预期 |
| 适用场景 | 需求模糊、需要探索 | 流程明确、步骤固定 |

举例：一个"自动下单"的流程。

- 固定 workflow：用户选商品 → 加入购物车 → 填地址 → 支付。每个步骤前后顺序固定，不应该让模型自己去"思考"要不要先支付再选商品。
- Agent 适合的场景：用户说"帮我做个市场调研，看看最近 AI 编程工具有什么新动向"。你不知道具体要查什么、怎么查，让模型自己决定先搜什么关键词、看哪些链接、怎么生成报告。

一个简单的判断标准：**如果你能用流程图把整个过程画出来，那就用固定 workflow。流程图画不清楚的部分，才是 Agent 的用武之地。**
