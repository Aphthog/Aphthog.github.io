第一次写需要查天气的助手时，我试过把天气 API 的返回结果全塞进 prompt 里——模型记住了一部分，但经常编造没查过的数据。后来才知道，LLM 的 API 原生支持"函数调用"（Function Calling），不需要自己拼 prompt。

## 模型其实不会调函数

首先说清楚：模型本身不会执行任何代码。它在你的服务器上跑，没有直接访问操作系统、网络或数据库的权限。但 API 设计了一个机制——模型可以"说"它想调用哪个函数、传什么参数，然后由你在本地执行，把结果送回给模型。

```
你: 今天北京天气怎么样？
        ↓ (把问题和函数定义一起发给模型)
模型: 我想调 get_weather(city="北京")
        ↓ (你拿到 tool_calls 字段)
你: 本地执行 get_weather，拿到结果
        ↓ (把结果回填给模型)
模型: 今天北京晴，25-32°C。
```

## 一次完整的往返

第一步：定义工具。告诉模型它能调用哪些函数，以 JSON Schema 格式描述参数：

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "获取指定城市的天气",
    "parameters": {
      "type": "object",
      "properties": {
        "city": { "type": "string", "description": "城市名" },
        "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
      },
      "required": ["city"]
    }
  }
}
```

第二步：把用户问题和工具定义一起发给模型 API。模型判断"这个问题需要调函数"，在返回的 `tool_calls` 字段里告诉你要调用哪个函数、参数是什么。

第三步：你在本地执行这个函数。不是模型在调——是你的代码在调。

第四步：把函数返回的结果以 `tool` 角色的消息回传给模型。模型据此生成最终回复给用户。

OpenAI 和 Claude 都支持类似的机制（Claude 叫 tool use），流程完全一样。

## 参数 schema 由谁校验

一个容易混淆的问题是：参数校验该谁做？

**格式校验**（类型对不对、要不要必填字段）——模型 API 在你发送工具定义时会帮你校验。如果你的定义有语法错误，API 会直接报错。

**语义校验**（值合不合理、有没有权限）——你的代码来做。模型可能生成不合法的参数值，比如让用户查一个不存在的城市。你应该在本地调用函数之前做验证，验证失败时把错误信息当作结果回给模型，让它重新生成参数或向用户说明。

## 两个常见坑

### 模型编造参数

模型不是严格遵循 schema 的机器，它可能"自由发挥"。比如你的函数要求 `date` 字段格式为 `YYYY-MM-DD`，模型可能传 `"2025年11月8号"`。或者工具定义里说 `unit` 只能是 `celsius` 或 `fahrenheit`，模型传了一个 `"C"`。

应对方式：本地加一层参数校验，捕获异常后回传错误消息让模型重新生成。

### 陷入循环调用

模型在某个函数上反复调用，每次都得到相同的结果，然后继续调用。比如查一个 API 返回空数据，模型觉得"没查到，我再试一次"，然后无限循环下去。

这不是模型不聪明，是它"觉得"再试一次可能就有结果了。要防止这个问题，**必须在调用循环上加总次数上限**。常见的做法是限制单次对话中 tool calls 不超过 5–10 次，超过就返回"无法获取"给用户。

| 问题 | 表象 | 解决 |
|------|------|------|
| 参数编造 | 格式错误、值不合法 | 本地校验，失败回传错误 |
| 循环调用 | 同一函数反复调 | 设置总轮数上限 |

Function Calling 是让模型从"聊天玩具"变成"可用工具"的关键能力。它让模型能访问外部世界的数据和服务，但前提是你得在工程上做好参数校验和循环保护——模型的能力很棒，但它不会替你管理调用安全。
