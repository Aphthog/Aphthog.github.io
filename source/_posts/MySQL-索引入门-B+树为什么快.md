大三做课设的时候写了一个选课系统，MySQL 里一张选课记录表，几千条数据，查起来飞快。我心想数据库也就这么回事。后来实习，线上一个订单表几百万行，`WHERE order_status = 0` 的查询跑了三秒多。我才意识到，"快"是有前提的——数据量小的时候全表扫描也能接受，数据量一大，没有索引就是灾难。

为什么不直接全表扫描？MySQL 默认把数据存在磁盘上（即使 SSD 也比内存慢几个数量级），全表扫描意味着把一整张表的每个数据页都从磁盘读到内存来判断。假设一个页 16KB，一张 500 万行的表大概占 500MB 以上的空间——每次查询都读一遍，磁盘 IO 次数非常可观。

索引的本质就是**拿空间换时间**：建一个额外的数据结构，帮 MySQL 快速定位到目标行，不用从头翻到尾。

## 为什么不是二叉树

二叉树（BST）在最坏情况下退化成链表，IO 次数等于树高。就算用 AVL 树或者红黑树保持平衡，每个节点只存一个 key，树高仍然可观。InnoDB 一个数据页 16KB，二叉树每个节点存几十字节就占满一页，树高轻松十几二十层，查一次走二十次磁盘 IO，跟全表扫描差别不大。

## 为什么不是哈希

哈希索引的致命弱点是**不能做范围查询**。`WHERE id > 100` 这类条件，哈希表只能全扫。而且哈希碰撞处理不好也有性能损失。MySQL 的 Memory 引擎支持哈希索引，但 InnoDB 只用它做自适应哈希索引——一种自动优化的加速手段，不是用户能主动建的主要索引结构。

## 为什么是 B+ 树

B+ 树解决了两个核心问题。

第一是**扇出大，树矮**。B+ 树的非叶子节点只存索引 key，不存实际数据。一个 16KB 的页，key 如果是 bigint（8 字节），指针大约 6 字节，一个页可以存大约 1170 个 key 和指针（16KB / 14 字节 ≈ 1170）。三层 B+ 树就能存 1170 × 1170 × 16 = 2000 万以上行数据。也就是说，查 2000 万行的表，最多只需要 3 次磁盘 IO。

第二是**范围查询友好**。B+ 树的叶子节点之间用双向链表串联，数据按 key 顺序排列。`WHERE id BETWEEN 100 AND 200` 查到 100 之后，顺着链表往后读就行，不需要回根节点重新遍历。这个特性对排序和范围条件很重要。

对比一下：

| 结构 | 单点查询 | 范围查询 | 磁盘 IO 次数（1000 万行） |
|------|---------|---------|------------------------|
| 哈希表 | O(1) | 不支持 | — |
| 红黑树 | O(logN) | O(logN) | ~24 次（树高约 24） |
| B+ 树 | O(logN) | O(logN)（链表） | 3–4 次 |

## 聚簇索引和二级索引

InnoDB 的表数据本身就是一棵 B+ 树，叫**聚簇索引**——叶子节点存的是整行数据。建表时指定的主键就是聚簇索引；如果没有主键，InnoDB 会选一个唯一非空列，或者自己生成一个隐藏的 `row_id`。

其他索引（比如 `CREATE INDEX idx_name ON t(name)`）叫**二级索引**，它的叶子节点存的是主键值。所以通过二级索引查数据需要两步：先找到主键，再回聚簇索引查整行——这叫**回表**。这个概念后面还会用到，这里先记住就行。

## 总结

MySQL 选 B+ 树做索引不是巧合。相比二叉树，它树矮、IO 少；相比哈希表，它支持范围查询和排序。非叶子节点不存数据这个设计，让每个页能装更多 key，三层就能撑住千万级数据。对于绝大多数业务系统的数据量，B+ 树的磁盘 IO 开销是稳定的常数级别。写 SQL 的时候多问自己一句"这个查询能走索引吗"，就是优化的第一步。
