有朋友第一次用 ChatGPT 问"今天天气怎么样"，模型回答说"我的知识截止到 2025 年"——他说不是，我是问今天天气。这个误会说明了一件事：模型知道的，是训练数据里截止某个时间点之前的内容。它不联网，不知道今天的新闻，不知道你公司内部的文档，也不知道你数据库里昨天新增的记录。

想让模型"知道"它没学过的东西，有几种做法。我项目里都试过一轮，优缺点很明显。

## 三种补知识的方式

### 1. 全部塞进 Prompt

最简单直接：把你需要的知识写到 prompt 里。比如你要模型回答你家产品的售后政策，就把政策文档全文贴在 prompt 里。

优点是没有架构变化，写一行 prompt 就行。缺点也很清楚：prompt 有 token 上限，知识一多就装不下。而且每次请求都把整份文档传一遍，成本按 token 算，频繁调用下来开销不小。适合知识量小、调用量低的场景——比如内部小工具，一次性问 5 道题。

### 2. 微调

把新知识直接训练进模型参数。优点是模型本身就会"记住"这些内容，不需要每次在 prompt 里贴。缺点是贵、慢、不灵活。知识一更新就得重新微调一遍。而且微调后的模型可能在其他方面出现退化（灾难性遗忘）。

适合知识高度稳定且需要高频使用的场景——比如客服模型需要记住全套产品规格，而且规格一年才更新一次。但不适合今天改个参数明天加条政策的情况。

### 3. RAG（检索增强生成）

RAG 是这几种方式里最推荐的方案。它的思路不是让模型"记住"知识，而是帮模型在回答时"查到"知识。

| 方式 | 成本 | 更新难度 | 适合场景 |
|------|------|---------|---------|
| 全塞进 Prompt | 低（部署），高（每次使用） | 容易（改文案） | 知识量小、低频使用 |
| 微调 | 高（训练），低（使用） | 难（需重新训练） | 知识稳定、高频使用 |
| RAG | 中（搭建），中（每次检索+生成） | 容易（重新索引） | 知识量大、频繁更新 |

## RAG 的基本流程

RAG 说穿了不复杂，几个步骤：

1. **切块**：把大文档切成小段。不能太长（语义混在一起），不能太短（缺乏上下文）。常见做法是 256–512 个 token 一段，带 overlap。
2. **嵌入**：把每个文本块用嵌入模型转成向量。
3. **检索**：用户提问时，把问题也转成向量，在向量库里找最相似的几段。
4. **拼进上下文**：把检索到的文本块塞进 prompt，让模型基于这些内容回答。

```
用户提问 → 问题嵌入 → 向量检索（Top-K）→ 取到相关文本块
                                               ↓
用户提问 + 相关文本块 → 组装 Prompt → 模型生成回答
```

## 什么情况下 RAG 反而是过度设计

RAG 虽好，但不是万能的。什么时候不该用？

**知识量太小的时候。** 如果你的知识库只有 10 条固定规则，写在 prompt 里就可以了。专门为 10 条规则搭一套向量检索、切块、索引体系，纯属给自己找麻烦。

**内容不需要实时更新。** 如果你的知识半年才变一次，微调的成本摊下来反而比每次检索 + 生成更便宜。微调之后模型调用时不需要检索步骤，响应更快。

**查询模式高度固定。** 比如"查产品价格"这种，每个问题都是特定的参数查询。这时候 RAG 反而绕了远路——直接用数据库查不是更简单吗？RAG 的优势在于语义搜索，即你不知道用户会怎么表达他的需求，需要靠"语义近似"来找到相关内容。当查询精确可预测时，传统数据库就够用了。

我自己的经验是：先用"全塞 prompt"跑通你的 MVP。当 prompt 太长或者知识需要频繁更新了，再考虑上 RAG。不要为了时髦而卷技术栈。
