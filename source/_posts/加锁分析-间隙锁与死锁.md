第一次在线上遇到死锁是接手一个活动系统的计数器表。日志里有一条 `Deadlock found when trying to get lock; try restarting transaction`，我当时的第一反应是"我都没用显式锁，哪来的死锁？"后来才知道，InnoDB 的行锁和间隙锁在某些 SQL 下会自动触发加锁——你甚至没意识到它加了锁，死锁就已经发生了。

## 三种锁的区别

InnoDB 的锁不是一种，而是三种，用在不同场景。

**行锁（Record Lock）**：锁住索引上的某一条记录。`SELECT * FROM t WHERE id = 1 FOR UPDATE` 就是行锁。注意 InnoDB 的行锁是基于索引实现的——如果 WHERE 条件没有走索引，行锁会升级为表锁（实际上是锁住所有聚簇索引记录，效果等同于表锁）。

**间隙锁（Gap Lock）**：锁住两条记录之间的空隙。目的是阻止其他事务在这个间隙插入新记录。间隙锁只在 RR 隔离级别下生效，RC 下不会有间隙锁——这也是为什么很多团队把隔离级别降到 RC 来减少锁冲突。

**临键锁（Next-Key Lock）**：行锁 + 间隙锁的组合。锁住一个左开右闭的区间 `(a, b]`。InnoDB 在 RR 级别下默认加的就是临键锁——既锁住行，也锁住间隙，防止其他事务在之间插入。

举个例子，表里有 id 为 1、3、5 三行：

- id = 2 的间隙锁：锁范围 `(1, 3)`，阻止插入 id = 2
- id = 3 的临键锁：锁范围 `(1, 3]`，阻止插入 id = 2 和修改 id = 3
- id = 5 的临键锁：锁范围 `(3, 5]`

间隙锁的本质是解决幻读：如果事务 A `SELECT * FROM t WHERE id > 1 FOR UPDATE` 查到了 3 和 5，没有间隙锁的话，事务 B 插入 id = 2，事务 A 再查一遍就多了一行——这就是幻读。

## 两条 UPDATE 死锁的实例

死锁最常见的原因是两个事务以相反的加锁顺序访问同一组资源。下面是一个实际能触发死锁的场景：

表结构：

```sql
CREATE TABLE `inventory` (
  `id` int NOT NULL,
  `sku` varchar(20) NOT NULL,
  `stock` int DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_sku` (`sku`)
) ENGINE=InnoDB;
```

数据：`(1, 'sku_a', 100)`、`(2, 'sku_b', 100)`。

事务 A：
```sql
START TRANSACTION;
UPDATE inventory SET stock = stock - 1 WHERE sku = 'sku_a';
-- 然后做其他事
UPDATE inventory SET stock = stock - 1 WHERE sku = 'sku_b';
COMMIT;
```

事务 B：
```sql
START TRANSACTION;
UPDATE inventory SET stock = stock - 1 WHERE sku = 'sku_b';
-- 然后做其他事
UPDATE inventory SET stock = stock - 1 WHERE sku = 'sku_a';
COMMIT;
```

如果两个事务同时执行：A 锁了 sku_a，B 锁了 sku_b。然后 A 等 B 释放 sku_b，B 等 A 释放 sku_a——死锁。InnoDB 的死锁检测器会检测到这个循环等待，立即回滚其中一个事务（一般是锁得少的一方），并返回：

```
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

注意这是个真实能复现的例子——两条 UPDATE 在 RR 下对二级索引 sku 加临键锁，两个事务的加锁顺序相反，必然触发死锁。

## 减少死锁的实践

经历几次死锁之后，我总结了三条做法：

**1. 固定加锁顺序。** 就像上面的例子，如果约定所有事务都先锁 sku_a 再锁 sku_b，就不会出现循环等待。代码层面可以让 sku 排序后依次处理。

**2. 缩短事务时间。** 死锁的窗口期跟事务持续时间直接相关。不要在事务里做 HTTP 调用、复杂计算或者等待用户输入。从操作数据库到 COMMIT，越快越好。

**3. 避免无索引更新。** 如果 `WHERE` 条件没有走索引，InnoDB 会锁住聚簇索引的所有记录（效果相当于表锁）。锁的范围越大，死锁概率越高。保证 `UPDATE` 和 `DELETE` 的 WHERE 条件走索引，把锁的范围降到最小。

另外，线上设置 `innodb_lock_wait_timeout`（默认 50 秒）不要开太大。死锁发生时，等待 50 秒才报错和 1 秒就报错，影响面完全不同。

## 总结

大多数死锁不是程序逻辑有问题，而是两个事务对资源加锁的路径产生了交叉。理解行锁、间隙锁、临键锁的区别，知道什么 SQL 加了什么锁，写代码的时候就能有意识地避免加锁顺序的冲突。遇到死锁报错别慌，看日志里两个事务的 SQL，找出锁冲突的路径，固定顺序就行了。
