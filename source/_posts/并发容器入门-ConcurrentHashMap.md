之前给一个接口加本地缓存，图省事用了 `HashMap` 存"用户 ID -> token"，并发也不高，一直没出事。后来有个批量任务把 QPS 顶上去了几天，开始零星报"缓存里的 key 明明写过却查不到"，偶尔还有接口卡死。

查到最后，根子是那个 `HashMap`。这篇把当时搞明白的东西记一下：它为什么不能这么用，以及 `ConcurrentHashMap` 到底是怎么解决的。

## HashMap 在多线程下会出什么事

`HashMap` 从来就没打算支持并发读写。它的文档里写得很清楚，非线程安全。问题具体表现在两处，而且**JDK 7 和 JDK 8 表现不一样**，这个顺序别记反。

**JDK 7：扩容时可能死循环。** 那会儿 HashMap 的链表插入用的是头插法。多线程同时触发扩容、同时搬同一个桶里的元素时，两个线程的操作可能交错，把原本 a -> b 的链表接成 a -> b -> a 这种环。之后任何一次 `get` 走到这个桶，就会沿着环一直转，把 CPU 吃满。这个现象当年叫得挺响，是很多人第一次意识到"集合默认不是线程安全的"。

**JDK 8：改成尾插，环没了，但会丢数据。** JDK 8 把链表插入改成尾插，扩容时的成环问题基本消除。但别误会成"JDK 8 的 HashMap 就安全了"——它仍然不是。两个线程同时往同一个空桶里 `put`，都判断这个位置为空、都把自己的节点放进去，后写的那个就覆盖了前一个，这条数据直接消失。更常见的版本是 `size` 计数错乱：两个线程各自算好的新容量互相覆盖，最后 `size` 对不上实际元素个数。

我在本机做了个实验（JDK 17），8 个线程各写 10000 个不同的 key，期望总共 80000 条。下面是其中一次的输出（示例输出，实际丢多少条每次都会变）：

```
HashMap size           = 29706 (expect 80000)
ConcurrentHashMap size = 80000 (expect 80000)
```

`HashMap` 最后只剩不到 3 万条。丢得这么夸张是因为这些线程本来就很可能触发扩容，扩容期间的数据搬运是重灾区；但真实业务里不需要丢这么多也会出事——**丢一条就是一条**。

## ConcurrentHashMap 的解法（一）：分段锁

`ConcurrentHashMap` 从 JDK 5 就有了，最初的设计思路是**分段锁**（segment locking）。

它把整个哈希表拆成若干段（默认 16 段），每段其实是一张小的哈希表，配一把自己的锁。写操作只锁住**要操作的那一段**，其他段照常读写。这样并发度从"整张表一把锁"提升到 16 倍左右——理论上同时可以有 16 个线程各写各的段。

这个思路的意义在于，它把"锁的粒度"这个旋钮第一次拧到了对一个集合来说足够细的位置：不再是一张表一个锁，而是按数据分区各管各的。JDK 7 的 `ConcurrentHashMap` 就是这版实现。

## ConcurrentHashMap 的解法（二）：CAS + 头结点锁

JDK 8 又改了一次，把分段锁去掉了，换成更细的做法：

- **桶是空的**：直接对数组里那个槽位做 CAS，谁抢到谁放，不涉及锁；
- **桶里已有元素**：对**这个桶的头结点**加 `synchronized`，只锁这一个桶；
- 扩容也是分段的（多个线程可以协作搬运）。

对比一下锁的粒度：JDK 7 是"锁一段"，一段里有很多桶；JDK 8 是"锁一个桶"。粒度又细了一档。而且空桶插入避免了一切锁，这在插入密集的场景下省掉了大量开销。

这里值得记的不是那些实现细节，而是一个方法论：**并发容器优化的方向，一直是把锁的粒度往下切，能不用锁的地方就不上锁**。分段锁是切一下，桶级锁加 CAS 是再切一下。

顺带说个容易忽略的：`ConcurrentHashMap` 不允许 `key` 或 `value` 为 `null`，`HashMap` 可以。如果你从 `HashMap` 换成 `ConcurrentHashMap`，代码里那些"`get` 返回 `null` 就当作不存在"的判断会在遇到真正的 `null` 值时出错——`put` 的时候就直接抛 `NullPointerException` 了，不用等到 `get`。

## 复合操作用原子方法，不要 get 再 put

`ConcurrentHashMap` 的单个 `get` / `put` 是线程安全的，但**组合多个操作就不一定**。这是最容易踩的一个坑。

最典型的就是"先查后写"：

```java
// 错误写法：读-判断-写三步之间，别的线程随时可以插进来
Integer old = map.get(key);
if (old == null) {
    map.put(key, 1);
} else {
    map.put(key, old + 1);
}
```

这本质上和前面的 `i++` 是同一类问题：`get` 和 `put` 各自都安全，合在一起不安全。4 个线程各跑 20 万次，期望 800000，实测结果是：

```
get-then-put = 292247 (expect 800000)
merge        = 800000 (expect 800000)
```

`ConcurrentHashMap` 把常用的复合操作都做成了原子方法，直接换成它们就行：

| 需求 | 原子方法 |
|---|---|
| 不存在才放 | `putIfAbsent(key, value)` |
| 不存在才计算并放 | `computeIfAbsent(key, k -> ...)` |
| 读出旧值算新值再写回 | `compute(key, (k, v) -> ...)` |
| 合并 | `merge(key, value, Integer::sum)` |
| 存在才删 | `remove(key, value)` |

比如上面那段改成 `map.merge(key, 1, Integer::sum)` 就对了。要注意 `computeIfAbsent` 的映射函数里**不要做耗时操作或再去操作同一个 map**，它是在桶上加了锁执行的，映射函数慢，会把这个桶卡住。

## 收尾

`ConcurrentHashMap` 保证的是**单个操作**的原子性，不是"你这段业务逻辑"的原子性。如果逻辑里有"先判断缓存里有没有、没有再查库、再写回"这类复合流程，那还是得靠别的手段去防并发（比如分布式锁、或者接受重复查询）。搞清这一点，比记住分段锁的段数重要。

回到我那个 token 缓存，最后就是把 `HashMap` 换成 `ConcurrentHashMap`、把"先 get 再 put"改成 `putIfAbsent`，报错就没了。
