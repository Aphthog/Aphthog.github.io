有段时间我在做一个定时统计任务，逻辑很简单：四个线程分头处理数据，每处理一条就给一个计数器 `count++`，最后把 `count` 打出来。上线后发现这个数字平时少一点也就算了，有几次少了将近一半。

我第一反应是数据源有问题，查了半天，最后被同事一句话点醒："你这个 `count`，多线程下这么加是不对的。"后来才知道，`i++` 这种我闭着眼睛写的语句，藏着并发编程里最基础的坑。这篇把当时搞清楚的三个概念记一下——原子性、可见性、有序性。

## 原子性：i++ 不是一步

代码里 `count++` 看起来是一步，CPU 执行起来其实是三步：**读**出 `count` 的值到寄存器，**改**成加一，**写**回内存。

多线程下问题就出在"读"和"写"之间。假设 `count` 是 5，线程 A 读到 5，还没写回；线程 B 也读到 5，也算出 6 写回去；然后 A 才把 6 写回。两次加一，结果只涨了 1。这就是我那个统计任务少数据的来路。

要验证这一点，写个十几行就够（我本机是 JDK 17）：

```java
static int plain = 0;
// 4 个线程，每个循环 10 万次 plain++
```

跑了几次，`plain` 的结果是 121418、120499 这类数字，**都不是期望的 400000**。这种"丢更新"的问题，本质是复合操作不具备**原子性**——中间状态会被其他线程插进来。

对策通常是加锁（`synchronized` 或 `ReentrantLock`），或者用 `AtomicInteger` 这类基于 CAS 的原子类。把上面那段换成 `atomic.incrementAndGet()`，四次实验都稳定得到 400000。

## 可见性：一个线程的修改，另一个线程看不到

原子性说的是"操作被打断"，可见性说的是"改了别人看不见"。

现代 CPU 有多级缓存，线程读变量时不一定去主内存拿，可能一直读自己核心里缓存的值。写的时候也是先写本地缓存，什么时候同步回主内存、别核什么时候能看到，都没有保证。

JMM（Java 内存模型）定义了一个抽象模型来描述这件事：**所有变量都存在主内存，每个线程有自己的工作内存**，线程对变量的读写都在工作内存里做，线程之间只能通过主内存传递数据。工作内存里可能只是 CPU 缓存的抽象，也可能包含寄存器、编译器优化后的临时值。

```
        ┌──────────┐        ┌──────────┐
        │ 线程 A    │        │ 线程 B    │
        │ 工作内存  │        │ 工作内存  │
        └────┬─────┘        └─────┬────┘
             │                    │
             └────────┬───────────┘
                 ┌────▼─────┐
                 │  主内存   │
                 └──────────┘
```

这样一来，"A 改了 `flag = true`，B 还在循环里等 `flag`"就可能永远转不出来。解决它最轻的手段就是给 `flag` 加 `volatile`——`volatile` 写的值会立即刷回主内存，读的值也会从主内存重新读，别的线程就能及时看见。更彻底的说法是 `synchronized` 也会在释放锁时把工作内存写回主内存，所以它顺带解决了可见性。

## 有序性：指令重排

第三类问题最反直觉。编译器为了优化、CPU 为了流水线，**会在不影响单线程结果的前提下调整指令顺序**。单线程下你感觉不到，因为"不影响单线程结果"是前提；可这个前提在多线程下就不成立了。

最有名的例子是双重检查锁（DCL）单例：

```java
public class Singleton {
    private static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {              // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {      // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

`new Singleton()` 并不是原子操作，它至少分三步：分配内存、初始化对象、把引用赋给 `instance`。问题在于第 2 步和第 3 步可能被重排成"先把引用赋出去，再初始化"。这时候另一个线程走到第一次检查，看到 `instance != null`，直接拿着一个**构造还没完成的对象**去用了。

修法很简单——给 `instance` 加 `volatile`，禁止这种重排。这个例子值得记，是因为它展示了一种很隐蔽的错觉：代码看上去有双重检查、看上去加了锁，但重排能让它失效。

不过要说明的是，JDK 5 引入的新内存模型（JSR-133）让 `volatile` 真正能禁止这种重排——更早的 JMM 弱到连加了 `volatile` 都不保证修好。所以 DCL 只有在记得加 `volatile` 的前提下才是安全的，不加照样有问题。我把它当作理解"有序性"的教材，而不是一个需要天天防的线上炸弹。

## 三类问题与对策

把三个概念摆在一起看：

| 问题 | 一句话描述 | 典型症状 | 主要对策 |
|---|---|---|---|
| 原子性 | 操作被中断，中间状态被插队 | `i++` 少加 | `synchronized`、`ReentrantLock`、原子类 |
| 可见性 | 一个线程的修改，另一个线程看不到 | 循环等一个标志位，永远等不到 | `volatile`、`synchronized` |
| 有序性 | 指令被重排，单线程顺序被打乱 | 拿到未初始化完成的对象 | `volatile`、`synchronized`、`happens-before` 规则 |

这三类问题不是互斥的。一个 `synchronized` 块同时提供了原子性、可见性和有序性；`volatile` 只给后两个；原子类只解决原子性，且只解决**一个变量**上的原子性。搞清楚一个手段到底解决哪一类问题，比记住一堆名词有用得多。

## 收个尾

我那个统计任务最后的修法是把 `int count` 换成了 `AtomicInteger`，问题就没了。当时觉得很神奇，现在回头看它只是补齐了原子性这一块，可见性和有序性在里面的处理反而更容易被忽略。JMM 这类东西，最好还是先有一个具体的 bug 摆在面前，再去理解它到底在防什么——不然很容易读成一堆抽象名词。
