上半年花了两三个月，完整实践了一个拼团营销交易系统：从营销活动、折扣试算、交易锁单，到结算回调、退款逆向的整条链路。这个系列用四篇文章做一次系统性的复盘——这一篇先讲架构和分域，后面三篇分别拆折扣试算、库存一致性、结算回调与退款。

> 说明：工程基于小傅哥（bugstack.cn）开源的 DDD 拼团营销项目实践搭建，本系列的源码分析与踩坑总结来自我对整个工程的逐行阅读、本地调试与复盘。

## 先把系统边界画清楚

这是一个**拼团营销侧系统**，不碰支付、不碰商品库存。它和上游交易商城的关系是：

- 商城负责下单、支付、订单主流程；
- 这边负责回答四个问题：**活动能不能参加、优惠多少钱、队伍满没满、成团了通知谁**。

两边的衔接只有两条通道：商城支付成功后**回调**这边（结算），这边拼团状态变化后通过 HTTP/MQ **通知**商城（成团、失败）。没有同步的跨系统事务，全靠回调 + 补偿。

把边界画清楚的价值在后面处处体现：结算不用等支付结果（商城回调告诉你）、退款只管自己的状态机（拼团单/交易单各自的状态组合）、库存只有"组队名额"这一个概念（商品库存是商城的事）。**微服务设计里最重要的一步不是拆，而是想清楚哪些东西不归你管**。

## DDD 四层：依赖倒置怎么落地

工程按 DDD 四层切 Maven 模块：

```
group-buy-market-app             # 应用装配：启动类、配置、mybatis
group-buy-market-trigger         # 触发层：HTTP 接口、定时任务、MQ 消费
group-buy-market-domain          # 领域层：三个业务域，只有接口没有实现
group-buy-market-infrastructure  # 基础设施：仓储实现、DAO、Redis、DCC
group-buy-market-types           # 通用：枚举、异常、响应对象
```

关键的一条依赖规则：**domain 不依赖 infrastructure**。仓储接口（`ITradeRepository`、`IActivityRepository`、`ITagRepository`）定义在 domain，实现类（`TradeRepository` 等）放在 infrastructure 并打上 `@Repository`。领域服务里注入的是接口，Spring 在运行时把实现注进来。

这样做的直接收益：领域逻辑里看不到任何 SQL 和 Redis 命令，`occupyTeamStock(teamStockKey, recoveryTeamStockKey, target, validTime)` 这样的方法签名说的是业务语言。哪天要把 Redis 换成本地缓存、把 MyBatis 换成 JPA，领域层一行不动。

代价也有：接口和实现隔层跳转，读代码时要来回翻。我的体会是这套结构在项目超过 20 张表之后才开始"回本"——前期会嫌啰嗦，后期靠它续命。

## 三个域：按生命周期切，不按功能切

domain 下按业务切成三个域：

| 业务域 | 职责 | 核心表 |
|---|---|---|
| `activity` 营销活动域 | 活动配置、折扣试算、规则编排 | group_buy_activity、group_buy_discount、sc_sku_activity、sku |
| `tag` 人群标签域 | 人群圈选、批量打标、Bitmap 查询 | crowd_tags、crowd_tags_detail、crowd_tags_job |
| `trade` 交易域 | 锁单、结算、退款逆向、回调补偿 | group_buy_order、group_buy_order_list、notify_task |

10 张表各归其主。分域的依据是**生命周期**，不是页面或接口：

- 活动域的东西在**运营配置活动时就定了**——几折、满减多少、限定哪些人群、可以开几次团。变化频率低，读多写少；
- 标签域是**运营侧的批量数据活**——跑批任务把人群写进 Bitmap，和用户实时行为无关；
- 交易域处理**用户实时的锁单-支付-退款流转**，是整个系统并发压力和数据一致性压力的所在地。

三个域之间只通过仓储接口交互。`trade` 域锁单时要校验活动，调的是 `IActivityRepository` 接口，完全不碰活动域的表——表级别是隔离的。这是后续把某个域单独拆成微服务的伏笔：**先按域隔离了数据和接口，物理拆分才有可能**。

## tag 域深读：人群标签为什么用 Bitmap

营销活动经常只对特定人群开放（新客、某渠道用户）。判断"这个用户在不在人群里"，朴素方案是关系表 `crowd_tags_detail(tag_id, user_id)`，查询就是一条 `select ... where tag_id = ? and user_id = ?`。

问题在于这个查询在**试算接口的热路径上**——每个试算请求都要查一次。批量打标时一条 insert 一条记录，100 万人的标签就是 100 万行。

系统的方案是**关系表 + Redis Bitmap 双写**，查询走 Bitmap：

```java
// TagRepository.addCrowdTagsUserId —— 打标：关系表 + BitSet 双写
try {
    crowdTagsDetailDao.addCrowdTagsUserId(crowdTagsDetailReq);
} catch (DuplicateKeyException ignore) {
    // 忽略唯一索引冲突
}

// 获取BitSet
RBitSet bitSet = redisService.getBitSet(tagId);
bitSet.set(redisService.getIndexFromUserId(userId), true);
```

```java
// ActivityRepository.isTagCrowdRange —— 查询：O(1)，不带任何 DB 往返
RBitSet bitSet = redisService.getBitSet(tagId);
if (!bitSet.isExists()) return true;   // 没配人群 = 不限制，直接放行
return bitSet.get(redisService.getIndexFromUserId(userId));
```

两个细节值得注意：

1. `DuplicateKeyException` 直接吞掉——批处理任务重跑时同一用户重复打标是常态，唯一索引兜底比先查后插干净；
2. `isExists()` 的 fallback 是 `true`（放行）——**没有配置人群约束等于全员可参与**，把"空配置"解释成最宽松的语义，避免运营少配一步把活动配死。

### 内存账本：这张 Bitmap 到底省没省内存

面试里我一定会被问"为什么用 Bitmap"，这里把账算清楚，因为答案没有想象中理所当然。

用户到 offset 的映射用的是 MD5 取模：

```java
// IRedisService.getIndexFromUserId
MessageDigest md = MessageDigest.getInstance("MD5");
byte[] hashBytes = md.digest(userId.getBytes(StandardCharsets.UTF_8));
BigInteger bigInt = new BigInteger(1, hashBytes);
// 取模以确保索引在合理范围内
return bigInt.mod(BigInteger.valueOf(Integer.MAX_VALUE)).intValue();
```

**理想情况**：如果用户 ID 能映射到紧凑的连续区间（比如自增序号 0~999999），100 万用户的标签位图 = 100 万 bit ≈ **125 KB**。同样的 100 万行关系表，算上主键和 `(tag_id, user_id)` 唯一索引，几十 MB 起步——差两个数量级以上，"内存降低 80%+" 这种说法在这里完全站得住，甚至保守了。

**现实情况**：看上面那段代码，取模范围是 `Integer.MAX_VALUE` ≈ 21 亿。Redis bitmap 的大小由**最大 offset** 决定，不是用户数。MD5 均匀分布下，哪怕这个标签只有 1 个用户，他的 offset 也大概率落在几亿到二十几亿之间——这一个 bit 就把位图撑到 `offset / 8` ≈ **几十到两百多 MB**。用户越多，最大 offset 越逼近 21 亿，每个标签 key 稳定逼近 256 MB。

也就是说，**这套实现的收益在查询路径（O(1)、零 DB 压力），不在存储内存**——除非把取模范围压缩（比如 mod 1000 万，单 key 上限压到 1.25 MB），或者建一层"用户 → 紧凑序号"的映射，或者换 RoaringBitmap 这类稀疏位图压缩结构。

所以"用 Bitmap 省了 80% 内存"这句话在面试里我会先**定义对比口径**：对比的是"把标签明细全量拉到应用内存里做判断"的方案（100 万个 userId 的 Set，堆内存轻松上百 MB），位图方案应用侧只做一次 O(1) 查询、不加载明细——这个口径下降幅 80% 是保守的。同时主动讲出 MD5 大范围取模的坑和修复方向，比等面试官戳破要好得多。

## 面试追问预演

**Q: 为什么用 DDD 四层，不直接 controller-service-dao 三层？**
A: 核心是依赖倒置——仓储接口在 domain，实现在 infrastructure，领域逻辑不依赖存储细节。项目小的时候三层更快，但这个系统的库存、幂等、状态机逻辑密度高，隔离存储细节后单测可以不起数据库直接测领域服务。

**Q: 三个域怎么划分的？域之间怎么交互？**
A: 按生命周期切：活动域配置期定死、标签域运营跑批、交易域用户实时流转。域间只通过仓储接口交互，不跨域碰表，为将来拆微服务留了缝。

**Q: 人群标签为什么用 Bitmap？内存真的省吗？**
A: 省的是查询路径——O(1) 判断、无 DB 往返；存储上要先看 offset 映射：紧凑 ID 下 100 万人 125KB，但这套实现用 MD5 mod 21 亿，位图大小由最大 offset 决定，单 key 逼近 256MB，存储反而可能更大。修复方向是压缩取模范围或换 RoaringBitmap。

**Q: 打标任务重跑会不会重复插数据？**
A: 关系表有 (tag_id, user_id) 唯一索引，`DuplicateKeyException` 直接吞掉；Bitmap 的 `set` 天然幂等。
