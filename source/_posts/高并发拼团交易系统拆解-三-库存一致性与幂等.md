拼团组队库存是典型的热点计数：一支 2 人队，最后 1 个名额放出来，可能同时有几百个请求在抢。这一篇拆系统的防超卖组合拳，以及交易系统里无处不在的幂等。

> 系列目录见[第一篇](/2026/08/29/高并发拼团交易系统拆解-一-架构总览与领域分域/)。

## 总体思路：越便宜的层，挡掉越多的流量

防线共三层，流量的漏斗是这样的：

1. **Controller 预检**——纯内存/单次读，挡掉"队伍已满还在重试"的流量；
2. **Redis INCR 原子抢占**——真正的主力，99% 的并发在这里被裁决；
3. **MySQL 条件更新**——最终裁决，Redis 不是账本，DB 才是正确性边界。

**第一层**是锁单入口先查拼团进度，`targetCount == lockCount` 直接拒绝，请求根本不进领域逻辑。成本几乎为零，但挡掉的往往是最大的一股流量——满员的队伍会持续收到无效重试。

**第二层**是核心，完整看这段：

```java
// TradeRepository.occupyTeamStock
@Override
public boolean occupyTeamStock(String teamStockKey, String recoveryTeamStockKey,
                               Integer target, Integer validTime) {
    // 失败恢复量
    Long recoveryCount = redisService.getAtomicLong(recoveryTeamStockKey);
    recoveryCount = null == recoveryCount ? 0 : recoveryCount;

    // 1. incr 得到值，与总量和恢复量做对比。恢复量为系统失败时候记录的量。
    // 2. 从有组队量开始，相当于已经有了一个占用量，所以要 +1
    long occupy = redisService.incr(teamStockKey) + 1;

    if (occupy > target + recoveryCount) {
        // 超出库存限制时，需要将已经增加的库存减回去，避免库存泄漏
        redisService.decr(teamStockKey);
        return false;
    }

    // 1. 给每个产生的值加锁为兜底设计，虽然 incr 操作是原子的，基本不会产生一样的值。
    //    但在实际生产中，遇到过集群的运维配置问题，以及业务运营配置数据问题，导致 incr 得到的值相同。
    // 2. validTime + 60 分钟，是一个延后时间的设计，让数据保留时间稍微长一些，便于排查问题。
    String lockKey = teamStockKey + Constants.UNDERLINE + occupy;
    Boolean lock = redisService.setNx(lockKey, validTime + 60, TimeUnit.MINUTES);

    if (!lock) {
        log.info("组队库存加锁失败 {}", lockKey);
    }
    return lock;
}
```

三个细节值得咀嚼：

1. **INCR 返回值即"排队号"**。每次 INCR 拿到全局唯一递增值，`occupy > target + recoveryCount` 一比对就知道超没超，超了立刻 DECR 回补。比"先 SETNX 抢名额、超了再回滚"少一次网络往返。
2. **恢复量 key 是独立的账本**。这是设计里最妙的一笔，下面单独讲。
3. **SET NX 兜底锁的来源是真实生产事故**。注释写得很直白：INCR 理论上原子且不重复，但"遇到过集群的运维配置问题，以及业务运营配置数据问题，导致 incr 得到的值相同"。给每个排队号再配一把锁，重复值就能被识别。**理论原子性和工程现实之间的差距，靠防御性设计来填**——`validTime + 60` 分钟的延长过期也是为了保留现场排查问题。

### 恢复量 key：为什么失败不直接 DECR

锁单流程是"先抢 Redis 库存 → 再落库"。落库失败时，占掉的名额要还回去。直觉做法是 DECR 占用 key，但这有个隐蔽问题：**占用计数里的每个值可能已经有主**（SET NX 锁着、请求还在往下走），直接 DECR 会把"计数减回去"，可那个名额对应的排队号和锁还挂着，账目就乱了。

系统的做法是失败时 INCR 一个独立的恢复量 key：

```java
// TradeLockOrderService —— 落库失败，记录失败恢复量并抛出
try {
    return repository.lockMarketPayOrder(groupBuyOrderAggregate);
} catch (Exception e) {
    // 记录失败恢复量
    repository.recoveryTeamStock(tradeLockRuleFilterBackEntity.getRecoveryTeamStockKey(),
                                 payActivityEntity.getValidTime());
    throw e;
}
```

判断阈值随之变成 `occupy > target + recoveryCount`：恢复的名额不回到"占用"里，而是抬高"可占总量"，让后来的请求可以重新占上。**失败退回的名额可以被重新使用，但两本账不混**——这比 DECR 回滚的方案多一个 key，少一类对不上的账。

## 责任链：锁单前的三道关卡

进入库存抢占之前，锁单请求要过一条责任链：**活动可用性 → 用户参与上限 → 组队库存抢占**。每个节点只做一件事，`return next(...)` 透传：

```java
// TeamStockOccupyRuleFilter —— 链上最后一环
// 1. teamId 为空，则为首次开团，不做拼团组队目标量库存限制
if (StringUtils.isBlank(teamId)) {
    return TradeLockRuleFilterBackEntity.builder()
            .userTakeOrderCount(dynamicContext.getUserTakeOrderCount())
            .build();
}

// 2. 抢占库存；通过抢占 Redis 缓存库存，来降低对数据库的操作压力。
boolean status = repository.occupyTeamStock(teamStockKey, recoveryTeamStockKey, target, validTime);
if (!status) {
    throw new AppException(ResponseCode.E0008);   // 缓存库存不足
}
```

注意"teamId 为空 = 首次开团不抢库存"——开团的人不需要名额判断（名额从 0 开始计数），只有加入已有队伍才要抢。责任链的价值在可插拔：以后要加黑名单过滤、渠道限制，加一个节点类、在工厂 `@Bean` 里添一个参数就行。节点间数据用 `DynamicContext` 传递（第一关查到的活动实体、第二关查到的参与次数），避免重复查库。

## 第三层：MySQL 条件更新，正确性的最终边界

Redis 挡了 99% 的流量，但 Redis 不是账本——主从延迟、持久化窗口、恢复量重放都可能造成计数偏差。落库时用条件更新做最终裁决：

```xml
<update id="updateAddLockCount" parameterType="java.lang.String">
    update group_buy_order
    set lock_count = lock_count + 1, update_time= now()
    where team_id = #{teamId} and lock_count &lt; target_count
</update>
```

`where lock_count < target_count` 让数据库自己保证不超卖——MySQL 对同一行的更新在行锁下是串行化的，并发请求排队过闸，闸门就是这条 where。影响行数不等于 1 说明拼团已满，抛异常回滚整个事务。**Redis 是性能优化，DB 的条件更新才是正确性边界**，这个主次关系在很多"Redis 库存"方案里被搞反了——把账本职责交给缓存，出了不一致连对账的基准都没有。

## 幂等：四处四把锁

交易系统里重复请求是常态：用户重复点击、MQ at-least-once 重试、定时任务重跑。这个系统四处幂等各有打法，原则统一——**唯一键 + 状态条件更新 + 抢占锁**：

1. **锁单幂等**：外部交易单号 `out_trade_no` 贯穿全链路。锁单先按它查已有记录，存在且未完成直接返回原结果；插入时唯一索引兜底，`DuplicateKeyException` 转业务异常。
2. **结算幂等**：状态流转全走条件更新（`where status = 0`），重复结算影响行数为 0，天然幂等。
3. **退款幂等**：责任链里有专门的 `UniqueRefundNodeFilter`，查到订单已 CLOSE 就返回 `REPEAT` 行为枚举，不重复执行退款。
4. **库存恢复幂等**：MQ 消费退单消息恢复库存时，`SET NX("refund_lock_" + orderId)` 防重复消费——同一订单的消息来两次，第二次拿不到锁直接跳过；消费抛异常主动删锁，让 MQ 下次重试还能进来。

### 一个真实的 bug：时间单位

复盘库存恢复这段代码时，我在 `refund2AddRecovery` 里发现一个真实的缺陷：

```java
// 本意：锁 30 天，防同一订单的退单消息被重复消费
// 实际：
redisService.setNx(lockKey, 30 * 24 * 60 * 60 * 1000L, TimeUnit.MINUTES);
//                          ^^^^^^^^^^^^^^^^^^^^^^ 毫秒值传进了"分钟"单位参数
```

`30*24*60*60*1000L` 是 30 天的**毫秒数**（25.9 亿），却传给了以**分钟**为单位的参数——实际过期时间约 5 万天，一百多年。幂等锁永不失效在这个场景里"歪打正着"地安全（锁越久越不会重复恢复库存），但如果这个订单要重新参与拼团，这把锁就成了永久路障。

教训记两条：**过期时间的数值和单位要当公式对待，不能心算**；以及读代码要带着"这段在什么条件下会坏"的眼光——单位不匹配这种 bug，功能测试根本测不出来，它只在时间维度上生效。

## 面试追问预演

**Q: INCR 之后服务挂了、DECR 没执行，库存不就少了？**
A: 少占的是"边缘名额"，且 DB 条件更新是最终裁决——Redis 少计只会让请求提前被拒，不会超卖。恢复量 key 再把落库失败的名额记账放回。极端对不上的情况，以 DB 数据为准做校准任务。

**Q: INCR 已经原子了，SET NX 有必要吗？**
A: 理论上没必要，但源码注释记录了真实生产案例：集群运维配置、运营配置数据问题导致 INCR 返回了相同值。SET NX 是给"小概率但发生过"的事故上的保险，成本是一次额外命令。

**Q: 为什么不用 Lua 脚本把 INCR + 判断 + DECR 原子化？**
A: 可以，Lua 是更彻底的方案。当前实现的 INCR/比较/DECR 之间没有依赖判断的中间状态暴露（比较基于返回值在应用侧做），竞态窗口不影响正确性——超占的那次 DECR 一定会执行。换 Lua 的收益是减少往返，不是修正确性。

**Q: Redis 和 DB 库存不一致怎么发现？**
A: 对账任务扫 DB 中 `lock_count` 与 Redis 计数比对；本系统里结算走 DB 条件更新，不一致的影响被限制在"多拒"或"多放后被 DB 拦下"，不产生资损。
