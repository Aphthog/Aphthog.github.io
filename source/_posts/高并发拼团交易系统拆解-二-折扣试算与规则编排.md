试算接口——用户打开拼团页看到"XX 元拼团结算"——是全系统流量最大的入口。这一篇拆它的两件事：**编排**（一堆校验和计算按什么顺序跑、怎么优雅降级）和**计算**（四种折扣怎么算、怎么扩展）。

> 系列目录见[第一篇](/2026/08/29/高并发拼团交易系统拆解-一-架构总览与领域分域/)。

## 规则树：把 if/else 编排成一棵树

试算的流程是：参数校验 → 降级/切量判断 → 拿活动配置和商品信息 → 算折扣 → 人群可见性判断 → 出结果。用 ifs 写就是一坨 200 行的主方法；这里把它编排成一棵规则树：

```
RootNode（参数校验）
   └─ SwitchNode（降级开关 / 切量判断）
        └─ MarketNode（异步装配数据 + 折扣计算）
             └─ TagNode（人群可见 / 可参与）
                  └─ EndNode（组装试算结果）
任何节点发现无配置 → 旁路 ErrorNode 兜底
```

树框架来自 wrench 的 `AbstractMultiThreadStrategyRouter`，每个节点实现两个方法：`doApply()`（本节点业务）和 `get()`（路由到哪个下级节点）。以 SwitchNode 为例：

```java
// SwitchNode.doApply —— 降级/切量两道闸
// 判断是否降级
if (repository.downgradeSwitch()) {
    log.info("拼团活动降级拦截 {}", userId);
    throw new AppException(ResponseCode.E0003.getCode(), ResponseCode.E0003.getInfo());
}

// 切量范围判断
if (!repository.cutRange(userId)) {
    log.info("拼团活动切量拦截 {}", userId);
    throw new AppException(ResponseCode.E0004.getCode(), ResponseCode.E0004.getInfo());
}

return router(requestParameter, dynamicContext);
```

```java
// MarketNode.get() —— 数据缺失走异常节点，否则进人群判断
// 不存在配置的拼团活动，走异常节点
if (null == dynamicContext.getGroupBuyActivityDiscountVO() || null == dynamicContext.getSkuVO() || null == dynamicContext.getDeductionPrice()) {
    return errorNode;
}
return tagNode;
```

TagNode 处理人群可见性，注意空配置的语义：

```java
// TagNode.doApply —— 人群标签配置为空，则走默认值
if (StringUtils.isBlank(tagId)) {
    dynamicContext.setVisible(true);
    dynamicContext.setEnable(true);
    return router(requestParameter, dynamicContext);
}

// 是否在人群范围内；visible、enable 如果值为 true 则表示没有配置拼团限制，直接置 true
boolean isWithin = repository.isTagCrowdRange(tagId, requestParameter.getUserId());
dynamicContext.setVisible(visible || isWithin);
dynamicContext.setEnable(enable || isWithin);
```

节点间的数据靠 `DynamicContext` 传递——SwitchNode 写开关结论、MarketNode 写活动配置/Sku/优惠价、TagNode 写可见性，EndNode 统一组装。**每个节点只读上下文、只写自己的字段**，加节点、调顺序都不碰别人的代码。

## DCC：开关为什么能"秒级生效"

SwitchNode 里那两个开关来自动态配置中心（DCC）：

```java
// DCCService —— 注解默认值：降级关、切量 100%
@DCCValue("downgradeSwitch:0")
private String downgradeSwitch;

@DCCValue("cutRange:100")
private String cutRange;
```

`@DCCValue` 是自研的一个注解（wrench 框架）：启动时把 `downgradeSwitch` 这个 key 以默认值 `0` 写进 Redis，并订阅这个 key 的变更；运营在管理端把值改成 `1`，Redis pub/sub 推到所有实例，字段值直接更新——**不重启、不发版，秒级把试算接口整体降级**。`cutRange` 同理：改成 `30` 就是只放 30% 的用户进来（按 userId 哈希），新功能灰度的标准打法。

大促场景里这类开关是保命符：下游 DB 有压力，第一反应不该是扩容，而是把非核心流量降掉。

## 策略模式 + Map 注入：路由不用工厂

四种折扣：直减（ZJ）、折扣（ZK）、满减（MJ）、N 元购（N）。路由的选择上我没有手写 `if/else`，也没有写工厂类——**用 Spring 自己当工厂**：

```java
// MarketNode.doApply
@Resource
private Map<String, IDiscountCalculateService> discountCalculateServiceMap;

// 优惠试算——按配置里的 marketPlan 取策略
IDiscountCalculateService discountCalculateService = discountCalculateServiceMap.get(groupBuyDiscount.getMarketPlan());
if (null == discountCalculateService) {
    log.info("不存在{}类型的折扣计算服务...", groupBuyDiscount.getMarketPlan());
    throw new AppException(ResponseCode.E0001.getCode(), ResponseCode.E0001.getInfo());
}

// 折扣价格
BigDecimal payPrice = discountCalculateService.calculate(requestParameter.getUserId(), skuVO.getOriginalPrice(), groupBuyDiscount);
```

每个实现类用 `@Service("MJ")` 这样的 bean name 注册，Spring 会把所有 `IDiscountCalculateService` 实现按名字收进这个 Map。**新增一种折扣 = 新增一个类，路由代码零改动**。比工厂模式少一层无意义的转发代码，比 if/else 少一处要维护的分支表。

## 模板方法：公共逻辑上提，子类只管算数

折扣计算有一段公共前置——限定人群的优惠要先过滤人群。这段逻辑收敛在抽象父类，用模板方法固定骨架：

```java
// AbstractDiscountCalculateService.calculate
@Override
public BigDecimal calculate(String userId, BigDecimal originalPrice,
                            GroupBuyActivityDiscountVO.GroupBuyDiscount groupBuyDiscount) {
    // 1. 人群标签过滤——限定人群的优惠，不在范围内按原价
    if (DiscountTypeEnum.TAG.equals(groupBuyDiscount.getDiscountType())){
        boolean isCrowdRange = filterTagId(userId, groupBuyDiscount.getTagId());
        if (!isCrowdRange) {
            return originalPrice;
        }
    }
    // 2. 折扣优惠计算——子类各自实现
    return doCalculate(originalPrice, groupBuyDiscount);
}
```

子类只关心自己的数学，比如满减 MJ：

```java
// MJCalculateService.doCalculate
// 折扣表达式 - "100,10" 即满100减10元
String[] split = marketExpr.split(Constants.SPLIT);
BigDecimal x = new BigDecimal(split[0].trim());
BigDecimal y = new BigDecimal(split[1].trim());

if (originalPrice.compareTo(x) < 0) {
    return originalPrice;                      // 不满足满减门槛，按原价
}
BigDecimal deductionPrice = originalPrice.subtract(y);
if (deductionPrice.compareTo(BigDecimal.ZERO) <= 0) {
    return new BigDecimal("0.01");             // 最低支付1分钱
}
return deductionPrice;
```

三类金额细节，是营销系统的红线：

- 全程 `BigDecimal`，比较用 `compareTo` 不用 `equals`（`equals` 连 scale 一起比，`1.0` 和 `1.00` 不相等）；
- 最终支付价 `setScale(0, RoundingMode.DOWN)` 向下取整——向上会让用户多付，向下是平台让利，**方向错了就是资损或客诉**；
- 兜底价 0.01 元而不是 0 元——0 元单在很多支付渠道走不通，也便于区分"免费"和"优惠到 0"。

## 异步装配：500ms 到 200ms 的推导

MarketNode 是树的计算核心，它需要两路数据：活动折扣配置、Sku 商品信息。两路查询相互独立，串行就是两次 DB 往返叠加。这里用线程池并行发起，统一 `get`：

```java
// MarketNode.multiThread —— 两路查询并行，再统一写入上下文
QueryGroupBuyActivityDiscountVOThreadTask queryTask =
        new QueryGroupBuyActivityDiscountVOThreadTask(..., repository);
FutureTask<GroupBuyActivityDiscountVO> activityTask = new FutureTask<>(queryTask);
threadPoolExecutor.execute(activityTask);

QuerySkuVOFromDBThreadTask skuTask = new QuerySkuVOFromDBThreadTask(goodsId, repository);
FutureTask<SkuVO> skuVOFutureTask = new FutureTask<>(skuTask);
threadPoolExecutor.execute(skuVOFutureTask);

// 写入上下文——前置查询数据，供后续节点直接取用
dynamicContext.setGroupBuyActivityDiscountVO(activityTask.get(timeout, TimeUnit.MILLISECONDS));
dynamicContext.setSkuVO(skuVOFutureTask.get(timeout, TimeUnit.MILLISECONDS));
```

### 数字怎么来的：面试时这么讲

串行耗时 ≈ `T活动查询 + T商品查询 + T计算`；并行后 ≈ `max(T活动查询, T商品查询) + T计算`。

假设单次 DB 查询 80~150ms（含网络往返 + MyBatis 映射），再叠加参数校验、序列化和树路由的固定开销：串行全链路 ≈ 400~600ms，并行后 ≈ 180~250ms。**500ms → 200ms 就是这么来的**——本地压测的观测值，绝对值随环境浮动，但量级可复现。面试时先讲结构（两路独立查询并行化、`get(timeout)` 统一收口），再给数字，并主动说明是本地压测口径——比报一个说不清来源的数字可信得多。

代码里还留了一个 `MarketNode2CompletableFuture` 的备选实现，源码注释里有张对比表，摘录要点：

| 对比维度 | FutureTask | CompletableFuture |
| :--- | :--- | :--- |
| 任务编排 | 弱（手动管理多个 Future） | 强（thenApply、allOf） |
| 代码简洁性 | 冗余（显式 get()） | 简洁（链式调用） |
| 异常处理 | 繁琐（逐个捕获） | 优雅（exceptionally 统一处理） |
| 适用场景 | 简单任务 | 复杂异步编排 |

两路并行这种简单场景，FutureTask 够用；如果以后要"查询 A 的结果作为查询 B 的入参"这种带依赖的编排，就该换 CompletableFuture。**切换实现只需换 `@Service` 注解**——树框架把节点隔离得足够好，换内核不动外壳。

## 面试追问预演

**Q: 为什么用规则树不是责任链？**
A: 责任链是线性的"过五关斩六将"，任何一关拦下就结束；试算的流程有分支和旁路（无配置走 ErrorNode、数据缺失跳计算），树结构的 `get()` 显式表达"下一步去哪"，语义更贴。锁单那种纯串联校验，系列第三篇会看到用的就是责任链。

**Q: 降级开关放 Redis，Redis 挂了怎么办？**
A: `@DCCValue` 注解字段在 JVM 内存里有默认值兜底（`downgradeSwitch:0`），Redis 不可达时读的是本地缓存值，不会因为配置中心故障导致接口不可用。

**Q: 线程池参数怎么配的？打满了怎么办？**
A: 核心数按 CPU 密集为主配小值，队列有界，拒绝策略抛异常快速失败——试算是入口接口，宁可拒绝也不能堆积拖垮整台机器。`get(timeout)` 里的 timeout 是最后一道闸，两路查询超过阈值直接走降级分支。

**Q: 金额为什么不能用 double？**
A: 二进制浮点表示不了 0.1 这类十进制小数，累加会漂移；营销侧金额计算错一分都是资损事故。BigDecimal + `compareTo` + 向下取整是组合拳。
