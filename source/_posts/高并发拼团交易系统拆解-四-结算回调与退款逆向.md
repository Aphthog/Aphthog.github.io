用户付完钱之后，故事才到一半：商城回调过来要结算成团，成团了要通知商城，用户要退款要逆向走一遍所有状态。正向流程决定了系统能不能用，逆向流程决定了系统敢不敢用。这一篇收尾。

> 系列目录见[第一篇](/2026/08/29/高并发拼团交易系统拆解-一-架构总览与领域分域/)。

## 结算：一个事务里的三连条件更新

商城支付成功后回调结算接口。核心是 `settlementMarketPayOrder`，在**同一个数据库事务**里完成三步条件更新：

```java
// 1. 交易单：CREATE -> COMPLETE（where status = 0）
// 2. 组队进度：complete_count + 1（where complete_count < target_count ... 语义同 lock_count 条件更新）
// 3. 满员时：拼团主单 status -> COMPLETE（where status = 0）
```

每一步都带状态条件，影响行数为 0 就抛异常回滚整个事务。源码里这段写着一条值得背下来的注释——**为什么用影响行数做判断而不是先查再改**：先查再改在并发下两步之间存在窗口（查的时候没满，改的时候满了），条件更新把判断和变更压缩成一次原子操作，这也是结算幂等的来源——重复回调时 `where status = 0` 不命中，影响行数 0，不会重复结算。

满员的最后一次结算会把拼团主单置为"完成"，同时**在同一事务里插入一条回调任务**：

```java
// TradeRepository.settlementMarketPayOrder —— 结算事务内
// 拼团完成写入回调任务记录
NotifyTask notifyTask = new NotifyTask();
notifyTask.setTeamId(groupBuyTeamEntity.getTeamId());
notifyTask.setNotifyCount(0);
notifyTask.setNotifyStatus(0);          // 0初始、1完成、2重试、3失败
notifyTask.setUuid(teamId + "_" + category + "_" + outTradeNo);   // 幂等键
notifyTask.setParameterJson(JSON.toJSONString(...));
notifyTaskDao.insert(notifyTask);       // 与结算更新同一事务
```

这就是**事务性发件箱（本地消息表）**，它解决的问题是：成团通知怎么保证不丢。

## 事务性发件箱：回调必达的笨办法和好办法

朴素做法是在结算事务里直接发 HTTP。两个死法：

- 事务里掺网络 IO 是反模式——HTTP 慢 3 秒，DB 连接被占 3 秒，高峰期连接池直接打穿；
- 时序无解——先发消息后提交，事务回滚对方收到"幽灵通知"；先提交后发消息，应用崩溃通知就丢了。

发件箱的方案是把"要发消息"这件事本身变成业务数据：**消息写入和业务变更同事务，要么一起成功要么一起失败**。剩下的就是怎么把表里的任务投递出去——"即时 + 补偿"双通道：

```java
// TradeTaskService.execNotifyJob —— 补偿通道的循环体
String response = port.groupBuyNotify(notifyTask);
if (NotifyTaskHTTPEnumVO.SUCCESS.getCode().equals(response)) {
    repository.updateNotifyTaskStatusSuccess(notifyTask);
} else if (NotifyTaskHTTPEnumVO.ERROR.getCode().equals(response)) {
    if (notifyTask.getNotifyCount() > 4) {
        repository.updateNotifyTaskStatusError(notifyTask);    // 彻底失败
    } else {
        repository.updateNotifyTaskStatusRetry(notifyTask);    // 继续重试
    }
}
```

- **即时通道**：结算事务一提交就扔线程池先试一把投递，绝大多数通知在一秒内送达，`notify_status` 直接置 1；
- **补偿通道**：定时任务扫 `notify_status in (0, 2)` 的记录重新投递，重试有上限——`notifyCount > 4` 标记彻底失败，防止下游挂掉时死循环打爆对方。

投递动作本身有并发防护，多实例部署时两把锁：

```java
// TradePort.groupBuyNotify —— 抢不到锁的实例直接放弃（等补偿任务）
RLock lock = redisClient.getLock(...);
boolean isLock = lock.tryLock(3, 0, TimeUnit.SECONDS);
if (!isLock) return null;
```

以及定时任务入口的 Redisson 抢占（`tryLock(3, 60, SECONDS)`）——**谁抢到谁执行，防的是 N 台机器把同一份通知发 N 遍**。整套设计与 Transactional Outbox 模式完全同构：没有 Canal、没有 Kafka 事务消息，一张表 + 一个定时任务换来至少一次投递保证。投递的是 at-least-once，所以下游（商城）还需要按 `uuid` 幂等去重——`teamId_category_outTradeNo` 这个幂等键就是为对方准备的。

## 超时未支付：定时逆向

锁单后不支付的订单要释放名额。`TimeoutRefundJob` 每分钟跑一次：

```java
// 扫描条件：status = 0（拼单中）and out_trade_time is null and now() > end_time limit 10
// 每条订单走退款逆向流程，把占用的名额还回去
```

两个细节：`limit 10` 是批量的节奏控制，一轮最多处理 10 条，处理不完下一轮继续，避免大结果集拖垮任务；入口的 Redisson `tryLock(3, 60, SECONDS)` 保证多实例只有一个在跑。

## 退款状态机：把路由写进枚举

退款是逆向流程的难点：拼团单有四种状态（拼单中/完成/失败/完成含退单），交易单有三种（锁定/完成/退单），两两组合九种，合法退款路径只有三种。把组合判断写成 if/else 会随状态增加而爆炸，这里的做法是**状态机直接写进枚举**：

```java
// RefundTypeEnumVO
UNPAID_UNLOCK("unpaid_unlock", "unpaid2RefundStrategy", "未支付，未成团") {
    @Override
    public boolean matches(GroupBuyOrderEnumVO groupBuyOrderEnumVO,
                           TradeOrderStatusEnumVO tradeOrderStatusEnumVO) {
        return GroupBuyOrderEnumVO.PROGRESS.equals(groupBuyOrderEnumVO)
                && TradeOrderStatusEnumVO.CREATE.equals(tradeOrderStatusEnumVO);
    }
},
PAID_UNFORMED("paid_unformed", "paid2RefundStrategy", "已支付，未成团") { ... },
PAID_FORMED("paid_formed", "paidTeam2RefundStrategy", "已支付，已成团") { ... };

public static RefundTypeEnumVO getRefundStrategy(GroupBuyOrderEnumVO group, TradeOrderStatusEnumVO trade) {
    return Arrays.stream(values())
            .filter(refundType -> refundType.matches(group, trade))
            .findFirst()
            .orElseThrow(() -> new RuntimeException("不支持的退款状态组合"));
}
```

每个枚举值自带 `matches()` 匹配自己的状态组合，非法组合在路由处就抛异常，不会漏到执行层。三种退款策略的差异用库存动作表达得最清楚：

- **未支付退单（UNPAID_UNLOCK）**：锁单量 -1，队伍名额重新打开，还能继续加人；
- **已支付未成团（PAID_UNFORMED）**：锁单量、完成量都 -1，人数缺口重新打开；
- **已成团退款（PAID_FORMED）**：最微妙——**锁单量不恢复**。队伍已经结算给了上游商城，动组队计数会影响已达成的交易；只把单状态改成"完成含退单"。如果队伍只剩这一个人，拼团直接转失败。

所有状态流转依然走条件更新，比如已成团退款：

```xml
<update id="paidTeam2Refund">
    update group_buy_order_list set status = 2
    where team_id = #{teamId} and order_id = #{orderId}
      and (status = 1 or status = 3) and complete_count = 1
</update>
```

并发退款、重复退单在 DB 层被最后拦截——和正向流程的原则一以贯之。

退单成功后，Redis 侧的库存恢复通过 MQ 异步完成，消费端三段式：本地消息表保证消息一定发出、`SET NX("refund_lock_" + orderId)` 保证不重复消费、MQ 重试保证失败必达——[第三篇](/2026/08/29/高并发拼团交易系统拆解-三-库存一致性与幂等/)里那个时间单位 bug 就藏在这段代码里。

## 写在最后：三个设计观

四篇写完，这个项目给我的最大收获不是"会用 Redis 和 MQ"，而是三个设计观的校准：

1. **正确性放 DB，性能放 Redis**。INCR 和条件更新各司其职，别让缓存承担账本的职责；
2. **幂等不是功能，是纪律**。四处幂等四处打法，原则统一：唯一键 + 状态条件更新 + 抢占锁；
3. **失败路径先于成功路径设计**。恢复量 key、notify_task 重试上限、退款策略的"库存不恢复"、定时补偿——这些"失败了怎么办"的代码量一点不比正常流程少，而这正是交易系统和 CRUD 的分水岭。

## 面试追问预演

**Q: 为什么不直接用 MQ 的事务消息/Canal 监听 binlog？**
A: 都能解，但引一个中间件的运维成本和这套"一张表 + 定时任务"不成比例。发件箱的缺点是补偿有延迟（秒级），对成团通知这个场景完全够用。如果通知时效要求高到秒级必达、或者下游订阅方变多，再升级到 MQ 方案——表结构不变，投递通道可换。

**Q: 重试上限为什么是 4 次？失败了人工介入？**
A: 4 次是防止下游长时间不可用时无限重试的止损值，不是精心调优的结果。置为失败态后这条记录不丢，修复下游后可以人工重置状态重新投递；更完善的做法是失败告警 + 管理端一键重试。

**Q: 已成团退款为什么不恢复锁单量？**
A: 队伍已结算给上游，组队计数代表"这笔交易发生过"，是和商城对账的依据；恢复它会让商城侧的成团记录和营销侧对不上。退款的金额口径在订单上（status = 2），库存口径留在队伍上。

**Q: 定时任务扫描会不会漏单/重复？**
A: 扫描按状态条件（status=0、超时时间）圈定，处理完状态就变，天然不重复；单轮 limit 10 防止大事务，堆积分轮消化。多实例靠 Redisson 抢占，同一时刻只有一个实例在扫。
